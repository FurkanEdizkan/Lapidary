# A2 — One storage location: browse, add, remove to `_removed/`

**Status:** open
**Branch:** `feat/one-storage`
**Wave:** 10 · **Kind:** Rust + web + deploy · **Depends on:** A1 · **Migrations:** 0064

## Why

Owner, 2026-10-17: one read-write storage location; Lapidary writes new files and moves removed ones, and never deletes a file. Models are added from an in-app file browser, with an optional page link and pictures.

## Decisions

Binding: [`ACCOUNTS.md`](ACCOUNTS.md), the plan the owner approved on 2026-10-17. Read the sections this goal names
before writing code.

## Done when

`/models` replaces `/ingest` and `/inbox`; `ModelStore` has no unlink; removing a model moves its file to `_removed/<user>/…` unless another part still points at it; the Import dialog browses, adds files and folders with a link and pictures; Fetch details fills a local model from its page without downloading.

## Record

- **One folder.**
  - compose mounts `${LAPIDARY_MODELS_DIR:-../models}` at `/models`, read-write. Both `LAPIDARY_INGEST_DIR` and
    `LAPIDARY_INBOX_DIR` point there.
  - The server makes the inbox the models folder when it is unset. `refuse_inbox_inside` is gone.
  - Uploads go to `uploads/<username>/…`, link imports to `imports/…`, examples to `examples/…`.
  - `.env.example` documents the `setfacl` for uid 10001, and the one-line `mv` for an upgrade.
- **Sources (`0064`).**
  - `library_source(path, kind, page_url, fetch_details)` and `library_source_image` replace `library.root`. An old root
    becomes the library's one source, and its parts' `source_path`s become paths under the models folder.
  - `app_user.fetch_details` is the Import dialog's starting answer.
  - A scan walks every source: a folder walked, a file taken as it is, the results de-duplicated. It never walks
    `_removed/`.
  - A part is named by its path under the models folder. A file filed as `Ingested` or `Revised` gets its source's
    pictures, once (keyed `lapidary:source/<id>/<n>`). When the source asked for it, the page's details are fetched
    inline, through a ten-minute page cache in `link.rs` (`ponytail:`), so a folder of thirty reads its page once.
- **Removal.**
  - `delete_parts` answers the `(root, path)` of each file no remaining row names.
  - `retire.rs` moves each one with `lapidary_storage::move_to_removed`: a `rename` to `_removed/<user>/<path>`, never over
    another file (`name (2).stl`), never an unlink.
  - `DELETE /api/parts/{id}` answers `200 {moved, stayed}`. Deleting a category moves its parts' files too.
  - Removing a source takes its parts out and moves no file.
  - `check-deploy`: the `/ingest`-read-only rule is gone. In `lapidary-api`, `move_to_removed` may appear only in
    `retire.rs`, and `remove_file`/`remove_dir` only in `upload.rs`.
- **Routes.**
  - `GET /api/storage/browse?path=`: folders, then model files; never `_removed`; at most 2000 entries.
  - `GET|POST /api/libraries/{id}/sources`, `DELETE …/sources/{source}`, `POST …/sources/{source}/pictures`.
  - `POST /api/parts/{id}/describe {url}` queues the new `describe_page` job (page only, nothing downloaded).
  - `GET|PUT /api/settings/import`.
- **Web.**
  - An **Import** button opens `ImportDialog`:
    - breadcrumbs and a list;
    - tick files or folders, or add the folder you are in;
    - an optional page link with "Fetch pictures, tags and licence", and optional pictures;
    - what the library holds, each with Remove;
    - links on to Upload and to Import from a page.
  - The order is the source, then its pictures, then one scan.
  - The part page's sources section has "Fetch details". Settings has "Adding models".
  - The delete wording says the file is moved into `_removed`.
- **Checks.**
  - The mover's unit test; source and picture ingest tests; `tests/added.rs` (browse, add, refusals, remove keeps files);
    the lifecycle test that a removed file is moved byte for byte; the `ImportDialog` test of the call order.
  - `verify slice`: 14 gates green.
  - Rig:
    - Sweep holds each top-level folder as a source. Lapidary's own folders are chowned to 10001 and left out of the
      fingerprint. Seed: 17 ok.
    - Flows: 25 ok. The delete flow now finds the file under `_removed/rig/uploads/rig/…`.
    - A real Chrome session added `misc/bracket-lp-1042-03.stl` with a real Printables page: the source was recorded, and
      the part arrived with the page's two pictures, with nothing downloaded.
- **Left.**
  - No in-app restore: move a file out of `_removed/` and add it again.
  - Two removals racing for one `_removed/` name in the same instant (`ponytail:` in the mover).
  - Per-user site keys and visibility are A3.
