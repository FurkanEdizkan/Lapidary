# F1 — Pictures without rendering

**Status:** ready, gate log target/verify-F1.log
**Branch:** `feat/embedded-thumbnails`
**Wave:** 7 · **Kind:** Rust + web · **Depends on:** S4 · **Migrations:** 0058

## Why

Since the pivot a card's picture is whatever a person uploaded. Many 3MF files already carry one: slicers write a
thumbnail into the package. And for an STL with no picture, the person who opens the viewer is looking at a perfectly
good one.

## Facts to check before building

- 3MF: the thumbnail is named by a relationship in `_rels/.rels` (type
  `http://schemas.openxmlformats.org/package/2006/relationships/metadata/thumbnail`), usually
  `/Metadata/thumbnail.png`; some slicers also write per-plate images (`Metadata/plate_1.png`). Use the
  relationship, fall back to nothing — not a guessed path.
- `crates/lapidary-cad/src/tmf.rs` already opens the package (its test at :781 builds one with a thumbnail).
- `crates/lapidary-api/src/images.rs::normalize` is the one path an image takes into `part_image`; ingest is in
  `lapidary-ingest`, so `normalize` may need to move to a crate both use (e.g. `lapidary-core` or a small module in
  `lapidary-storage`). Move it, don't copy it.
- `part_image.origin` check constraint: today's values, and that `og_fetched`/`rendered` have no writer.

## Rules

- A person's own picture always wins: an embedded thumbnail is added only to a part with no picture, and never
  replaces one.
- A broken or oversized embedded image is skipped with a logged reason; it never fails the ingest.
- The viewer's "use this view as the picture" uploads through the existing endpoint, origin `snapshot`.

## Stages

1. Embedded 3MF thumbnail at ingest, origin `embedded`. **Tests:** a 3MF with one gets a picture; one without
   gets none; one with a corrupt PNG ingests fine with no picture; a part with an uploaded picture keeps it.
2. Viewer button. **Tests:** web test for the button and the upload call.

## Done when

Ingesting slicer-saved 3MFs from the owner's corpus gives cards with pictures and no upload; the Record says how
many of the corpus's 3MFs carried one.

## Record

**Done.** A part gets a picture without anybody rendering one: the thumbnail a slicer saved inside its 3MF,
or the view somebody had on screen in the 3D viewer.

- **Embedded thumbnails.** `lapidary_cad::thumbnail_3mf` follows the package's OPC thumbnail relationship
  (`.../relationships/metadata/thumbnail`), never a guessed path, through one shared relationship lookup
  with the model's own. Capped at 10 MB, the upload limit. Ingest reads it right after the parse, while
  the bytes are in hand, and after the part is committed — new part or new revision — passes it through
  the same `normalize` every upload takes and stores it like the gallery does (inline under 64 KB, a blob
  above), origin `embedded`. Warn-only throughout: a broken thumbnail is a log line, never a failed ingest.
- **A person's picture always wins.** `PgParts::adopt_part_image` locks the part row, counts its gallery,
  and adds nothing when there is a picture — so a revised 3MF never replaces one somebody chose, and an
  upload racing it either comes first or sits after it. Mutation: dropping the guard fails
  `a_thumbnail_never_replaces_a_picture_somebody_chose` with `["uploaded", "embedded"]`.
- **The view as the picture.** The viewer offers *Use this view as the picture* once a part is drawn, on
  a recordable page, **and only for a part with no picture yet** (a snapshot joins the end of the
  gallery, so on a part that has one it would not be the card's picture the button promises). It draws
  one frame and reads the canvas in the same task, since without `preserveDrawingBuffer` a later read is
  blank, then posts it to `POST /api/parts/{id}/images?from=snapshot`: the same route and checks, origin
  `snapshot`; any other `from` is a 400 that stores nothing.
- **`normalize` moved to `lapidary-storage::images`** (it gained `image` and `tracing`), so an upload, a
  fetched URL and an embedded thumbnail are one code path. `lapidary-api` re-exports what it uses and
  still never links `lapidary-cad`.
- **0058** widens `part_image_known_origin` with `embedded` and `snapshot`. **Decided without the owner:**
  `og_fetched` and `rendered` stay in the check — nothing writes them, but an upgraded install may hold
  rows with them, and a check those rows fail would stop the migration.

**Found and fixed on the way: Bambu Studio and Orca 3MFs did not ingest at all.** Their projects use the
3MF Production extension: the main model's objects are only components pointing with `p:path` into
other model parts (`3D/Objects/object_N.model`), each numbering its objects from 1. The parser did not
follow `p:path`, so it refused every one with "a build item names object 1, which does not exist". It now
reads each referenced part once and files its objects by path and id. One unit per package (every
slicer writing `p:path` writes millimetres; a mixed package is refused by name — a `ponytail:` says where
the upgrade goes).

**Measured on the owner's corpus** (`/mnt/Storage2/All/STL Files`, 2026-10-16):
- **89 3MFs; all 89 carry a thumbnail relationship that resolves**, every one at
  `Auxiliaries/.thumbnails/thumbnail_3mf.png` — a guessed `Metadata/thumbnail.png` would have found none.
- Through a real stack, all 89 scanned in **90 s**: **84 ingested, every one of the 84 with its embedded
  picture**; the app peaked at 593 MiB of its 2 GiB. Before the `p:path` fix, 3 of the first 4 tried failed.
- **5 refused** by the reader's 8,000,000-triangle bomb guard: Bambu kits of 129–179 MB (`Tyrant`,
  `Immortal`, `Knight_Lancer`, `Questoris_V2`, `Warbringer_Pattern`). **Left for the owner:** they are
  real parts, not bombs; raising the cap costs 36 bytes a triangle (8 M is ~288 MB per job, two jobs at
  once), and it is a security control, so it is not changed here.

**Tests:** `thumbnail_3mf` (found through a relationship at an odd path, a stray PNG not taken, a dangling
target malformed); `p:path` components followed without confusing two objects numbered 1; three ingest
tests (a thumbnail arrives as `embedded`; none, and a truncated one, ingest with no picture; a chosen
