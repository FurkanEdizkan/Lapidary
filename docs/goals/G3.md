# G3 — Likeness API

**Status:** ready at af89e91, gate log target/verify-G3.log
**Branch:** `feat/likeness-api`
**Wave:** 1 · **Kind:** Rust · **Depends on:** W0 · **Migrations:** — (W0's 0047, 0048)

## Why

The part page, the review queue and the dashboard's duplicates widget all ask one question: which parts are like this
one, and what has somebody already decided about them. Design: [`phase-6.md`](phase-6.md) §§ Three kinds of alike;
Links, and folding.

## Facts checked (re-check against W0's merge)

- W0 gives `part_shape`, `part_link`, `PgShapes::record`, `PgParts::rows_by_id`, `to_card` (`pub(crate)`), the wire
  types `Likeness`, `DuplicateClusters`, `SetLink`, `FoldPart`, and `likeness::routes()` (empty).
- Soft delete is `PgParts::soft_delete`; Restore exists (`removed.tsx`). Cross-library requests answer 404 everywhere.

## Rules

- Owns: `crates/lapidary-db/src/likeness.rs` (new), the handlers in `crates/lapidary-api/src/likeness.rs`,
  `crates/lapidary-api/tests/likeness.rs`. Not `repo.rs`, not `lib.rs`'s route list (W0 merged `likeness::routes()`).
- Ranking and clustering are pure functions with their own unit tests; SQL only fetches candidates.
- Implement `pub(crate) async fn clusters(db, library, since)` exactly as W0 declared it — G4 calls it.

## Stages

1. **Reads** — profiles by library; candidates in the ±2% size band; identical by current source `blake3`; links of a
   part. **Routes:** `GET /api/parts/{id}/likeness?limit=24`, `GET /api/libraries/{id}/duplicates?since=`.
2. **Decisions** — `PUT` / `DELETE /api/parts/{id}/links/{other}` (`variant`, `distinct`); `POST /api/parts/{id}/fold`
   `{ into }` in one transaction (soft-delete by the `soft_delete` rule + a `folded_into` row);
   `GET /api/libraries/{id}/folds`.
3. **Tests** (synthetic profiles through `PgShapes::record`): identical-by-hash appears; a scaled copy is similar but
   not a near-duplicate; `distinct` and `variant` take the pair out of clusters, and a variant shows on both parts;
   pairs A–B and B–C make one cluster; fold soft-removes, Restore brings the pair back; fold refuses another library
   (404), itself (422), a removed target (404); removed parts are excluded; `since` filters.
4. **Measured:** 10,000 synthetic profiles, release build, warm — `/likeness` under 50 ms, `/duplicates` under 300 ms.
5. Mutation checks: the size band dropped; the `distinct` link ignored; fold without the soft delete.

## Record

**Built.** `crates/lapidary-db/src/likeness.rs` (new) and the handlers in
`crates/lapidary-api/src/likeness.rs`, filling W0's empty `routes()` and its `clusters()` stub. The
`#[allow(dead_code)]` on `lib.rs`'s `mod likeness` line is gone. No wire type changed — G6 builds
against exactly what W0 landed — and no new `#[ts(export)]` type exists, so `web/src/bindings` is
untouched.

- **Routes:** `GET /api/parts/{id}/likeness?limit=24` (default 24, clamped to 1–96; an unreadable
  `limit` is the default rather than a 400, as `parts.rs` decided for `after=&limit=`),
  `GET /api/libraries/{id}/duplicates?since=`, `PUT`/`DELETE /api/parts/{id}/links/{other}`,
  `POST /api/parts/{id}/fold`, `GET /api/libraries/{id}/folds`.
- **Db:** `PgLikeness` with five reads and three writes — `shapes(library)` (current profiles off
  `part_shape_size`, smallest first), `parts(library)` (live parts, `created_at`, current source
  `blake3`), `identical(library, part)` (driven off `file_blake3`; it finds the part's own hash in
  SQL so there is one definition of "this part's current bytes"), `links(library, of)`, `folds`,
  and `set_link` / `unlink` / `fold`.
- **Pure functions, unit-tested in the same file:** `alike` ranks a library's profiles against one
  part's, ties broken on id; `clusters` sweeps the size-ordered profiles, stops at the first
  candidate past the size band, and unions the undecided pairs plus the same-bytes groups — so A
  like B and B like C is one group of three, not two overlapping questions.

**Measured** (10,000 synthetic profiles through `PgShapes::record`, release, warm, median of seven
runs through `router().oneshot` so card building counts; lane 1's database on 55433):

| | Budget | Median | Runs |
|---|---|---|---|
| `/likeness` | 50 ms | **26.6 ms** | 25.0 / 25.7 / 26.2 / 26.6 / 27.2 / 27.8 / 29.3 ms |
| `/duplicates` | 300 ms | **234.0 ms** | 231.7 / 233.4 / 233.5 / 234.0 / 236.0 / 238.0 / 251.3 ms |

**That `/duplicates` figure is close to a worst case, deliberately reported as one.** The corpus's
descriptors are 0.01 apart and its sizes 0.5 mm apart, so above about 25 mm nearly every part is a
near-duplicate of its neighbour: the answer was **119 clusters holding 9,991 of the 10,000 parts**, 0
unprofiled. So the 234 ms is mostly `rows_by_id` building and serialising 9,991 cards with inline
thumbnails, not the two reads and not the ranking. A real library with few duplicates does strictly
less work — the same `parts()`, `shapes()` and band-bounded sweep, and far fewer cards — which makes
this an upper bound rather than a typical figure. The measurement prints those counts.

Seeding those 10,000 parts takes about 12 s. The measurement is `#[ignore]`d
(`ten_thousand_profiles_answer_both_routes_inside_their_budgets`), because the gate should not pay
that to learn a number that belongs here; it asserts both budgets when run:
`cargo xtask heavy -- cargo test --release -p lapidary-api --test likeness -- --ignored --nocapture`.

**Tests.** `crates/lapidary-api/tests/likeness.rs` 13 + 1 ignored; `lapidary-db`'s unit tests 8.
Covered: identical-by-hash with no profile at all; a scaled copy is similar and never a
near-duplicate, asserted on both routes; `distinct` and `variant` take a pair out of the queue and a
variant shows on both parts; undoing a decision proposes the pair again and a second undo is a 404;
A–B and B–C are one cluster; identical clusters say `identical: true`; a profile of an older revision
is not a profile (`profiled: false`, out of the clusters, counted in `unprofiled`); removed parts are
out of every list; `since` filters and `?since=` empty is no filter while `?since=yesterday` is a
400; fold removes, the folds list names it, Restore brings the pair back and an ordinary removal
afterwards stops it being a fold; fold refuses itself (422) and a removed target (404).

`two_libraries_never_see_each_other` is the tenant test, and it is a real one: the same file name, the
same bytes and the same profile in two libraries, so everything that could make them one part is true
except the one thing that matters. Fold is 404, the decision is 404, and neither library's likeness or
duplicates names the other's part. The earlier "another library" cases used a `PartId::new()`, which
names no library at all and so only proved that a nonexistent part is a 404.

**Mutation checks** (each rule broken on purpose, the failing test named, then restored):

| Broken | Fails |
|---|---|

| the sweep's band dropped as well | `a_scaled_copy_is_no_cluster` too |
| the `distinct` check dropped | `a_decided_pair_is_never_a_cluster`, `a_decided_pair_leaves_the_near_duplicates_and_a_listed_one_leaves_both`, and the api's `distinct_takes_a_pair_out_of_the_queue…` |

| the staleness check removed | `a_profile_of_an_older_revision_is_not_a_profile` |
| `fold`'s `b.library_id = a.library_id` dropped | `two_libraries_never_see_each_other` |
| `both_live`'s `library_id = $2` dropped | `two_libraries_never_see_each_other` |
| the `folds` stamp equality replaced by `deleted_at IS NOT NULL` | `a_fold_removes_the_duplicate_and_restore_brings_the_pair_back` |

The two **write** guards are what those tenant mutations check. The reads' `library_id` filters are
not checked the same way, and cannot be from a route: `rows_by_id(library, …)` filters a foreign
part's card out downstream, so dropping `library_id` from `shapes` or `identical` still answers
correctly. That is defence in depth rather than an untested rule, but it is worth knowing.

**Decided without asking.**

1. **"Current profile" is `SHAPE_VERSION` + no newer revision, not the L0 hash.** `shapes.rs`'s doc
   calls a row stale when its `l0_blake3` is not the current L0's as well. Checking that needs the L0
   derivative of the current revision — a second lateral a row on the 50 ms path — and catches one
   case only: an L0 rebuilt for the same revision without a version bump, which is G2's job to
   notice. The revision half is kept and spelled `NOT EXISTS (… n.id > ps.revision_id)`, on the UUID
   v7 ordering `PgShapes::record`'s own guard already rests on. That spelling matters: the obvious
   `= (SELECT id … ORDER BY created_at DESC LIMIT 1)` cost 29 ms of a 52 ms `/likeness` — over
   budget — and a `DISTINCT ON` CTE over the library's revisions was worse still at 77 ms. One
   definition serves `profiled`, `unprofiled` and both routes, so they never disagree about what has
   been compared.
2. **One full-library profile read serves both routes.** `similar` ("more like this") needs every
   profile whatever its size, so the ±2% band is applied in Rust over the size-ordered rows rather
   than as a second SQL query. `part_shape_size` still provides the order, and the sweep still stops
   at the first candidate past the band.
3. **A `distinct` part stays in `similar`.** "Never propose again" is about the duplicate queue; a
   part somebody said is not the same is still a reasonable thing to reach through "more like this".
   It is out of `near_duplicates` and out of every cluster.
4. **A fold's removal and its link share one stamp.** `now()` is the transaction's, so
   `part.deleted_at = part_link.created_at` exactly for a real fold, and `folds` reads that equality
   back. Without it, fold → Restore → ordinary remove would leave the removed page claiming the part
   was folded into something, which is false. Nothing in `repo.rs` or `lifecycle.rs` was touched to
   get this.
5. **`set_link` and `fold` clear whatever the pair was before.** One row a pair, whichever way round
   it was decided, so a `folded_into` row left by a restored fold cannot sit beside a later
   `variant`. A `folded_into` row is not removable through `DELETE …/links/{other}` — the way back
   from a fold is Restore.
6. **The folds list names a kept part that was itself removed since.** Two `rows_by_id` calls, `Live`
   then `Removed`: "folded into X" is true whether or not X is in the library today. A *purged* X
   takes its row with it, as `phase-6.md` says, and the entry simply is not there.
7. **Both library routes answer 404 through `PgParts::auto_thumbnail`**, the existence probe
   `derive.rs` already uses, with a read-side wording of its own.
