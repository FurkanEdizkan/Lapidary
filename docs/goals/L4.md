# L4 — A query that gave up stops running

**Status:** ready at 2d85a0c, gate log target/verify-L4.log
**Branch:** `fix/statement-timeouts`
**Wave:** 3 · **Kind:** Rust (small) · **Depends on:** G4 (its test proves the hole) · **Migrations:** —

## Why

Found by G4 while building the dashboard's resolve (2026-09-27), and it is the kind of hole that only shows up when
somebody writes the adversarial test: **a timeout in Rust bounds how long a caller waits, not how long the statement
runs.** Dropping the future cancels nothing on the server, and sqlx cannot return that connection to the pool until
Postgres finishes answering. G4's `a_key_that_gave_up_still_holds_its_connection_until_the_lock_clears` demonstrates it
on a pool of one.

So the resolve route's semaphore bounds how many keys **wait** at once, not how many connections keys that already gave
up are still holding. With a table lock held long enough, repeated resolves can drain a pool of eight and stall
everything else the api serves — the grid, the open path, a download. The dashboard is only where it was noticed;
anything that times out a query has it.

`FEATURES.md` §8 calls per-widget polling a self-inflicted DoS. This is the same shape, one layer down.

## Facts to check before building

- Where the pool is built: `lapidary_db::connect` (`crates/lapidary-db/src/lib.rs`), `max_connections(8)`, and what the
  worker's pool sets differently from the api's — a background job that legitimately runs for minutes must not inherit a
  two-second ceiling.
- **The api now serves on seven of those eight** (found by G1, 2026-09-27): `PgListener::connect_with` calls
  `pool.acquire()` and holds that connection for the life of the process, so the event stream permanently costs one.
  G4's semaphore of four was sized against eight. Not a correctness problem on its own, and it makes this goal's
  arithmetic tighter: four keys that gave up, each still pinning a connection, plus the listener, is five of seven.
- `sqlx::postgres::PgConnectOptions::options` (or `after_connect`) for `statement_timeout` and `lock_timeout`, and
  whether the value belongs on the pool, the role, or the transaction.
- G4's `dashboard.rs`: the 2 s per key starts after its permit, and the queue widget's read is the one the test locks.
- Whether any existing read legitimately exceeds the ceiling this goal picks — the bundle plan, `instance_storage`'s
  disk walk (which G4 already skips), the purge and its recompute, `enqueue_stale_shapes`.

## Rules

- **Server-side, not another Rust timeout.** A second `tokio::time::timeout` would repeat the bug.
- **The api and the worker get different ceilings**, and the difference is stated where it is set. A job that tessellates
  for a minute is not a stuck query.
- An abandoned statement must free its connection *and* say so once, in the api's log, with the widget or route named —
  silence here is what made this invisible until somebody locked a table on purpose.
- The error a caller sees still follows CLAUDE.md: what broke, what to do. A raw `57014 query_canceled` is not that.

## Stages

1. **The ceiling** — `statement_timeout` and `lock_timeout` on the api's pool, chosen against the slowest legitimate
   read, and the worker's pool left long. **Tests:** a statement past the ceiling is cancelled server-side and its
   connection is back in the pool immediately (G4's test, inverted — it should now pass with a pool of one); a worker
   job longer than the api's ceiling still finishes.
2. **The resolve path** — a `timedOut` key no longer pins a connection; twelve keys against a locked table leave the pool
   with eight connections free. **Tests:** repeat G4's lock scenario in a loop and assert the pool never starves — the
   thing that could not be tested before.
3. **Say it once** — the cancelled statement is logged with its route or widget, at warn, without a per-row storm.

## Done when

G4's pinned-connection test passes with the ceiling in place, a locked table cannot starve the pool however many
resolves arrive, a long worker job is unaffected, and `verify slice` is green.

### What it is, in one line

The api's pool now carries `statement_timeout` and `lock_timeout` in its connection's **startup
options**, so a read nobody is waiting for any more is stopped by PostgreSQL and its connection comes
straight back. `lapidary_db::connect` takes a `Ceiling`; `bin/lapidary-server`'s `ceiling_of` is where
a role becomes one.

### The ceilings, and why these numbers

| | `statement_timeout` | `lock_timeout` | Who |
|---|---|---|---|
| `lapidary_db::INTERACTIVE` | **5 s** | **2 s** | api, peer |
| `lapidary_db::BACKGROUND` | **10 min** | **2 min** | worker |

- **5 s is twenty times the slowest api read anybody has measured** — `GET
  /api/libraries/{id}/duplicates`, 234 ms over 10,000 parts that are nearly all near-duplicates
  (G3's figure, and the ROADMAP calls it an upper bound). Nothing legitimate is near it; what it
  bounds is how long a caller that has already given up can keep a connection.
- **2 s for a lock is the dashboard's own per-widget budget**, which is the point: a locked table is
  now what a widget *reports* rather than what it waits through, and G4's two timing tests pass
  unchanged because the number that ends a blocked tile is still two seconds — it is just the
  server's now.
- **The lock ceiling is below the statement ceiling on both roles.** `statement_timeout` counts a
  lock wait too, so an equal or higher `lock_timeout` could never fire, and the api would lose the
  one cancellation that names contention.
- **The worker's two are backstops, not budgets.** Its statements are nowhere near either; the
  numbers exist so a runaway one cannot pin a connection for the life of the process. Checked
  against the two places it holds a lock across slow work: `claim_hash` holds an advisory lock
  across a file copy but takes it with `pg_try_advisory_xact_lock`, so it never waits, and a
  revision holds its part row across `write_manifest`.
- **Migrations are outside both**, and were already: `migrate` builds its own pool from the URL
  alone. That is load-bearing now — `0002_parts.sql` is ~1.4 s of DDL and the migrator's advisory
  lock waits ~2.1 s while another container holds it, both past `INTERACTIVE`'s lock ceiling and
  both the system working (`MIGRATION_SLOW_STATEMENT`'s doc measured them).
- **`lock_timeout` does apply to `pg_advisory_xact_lock`**, checked against PostgreSQL 18 on lane
  1's database before anything was written, because `PgFolders::reparent` takes one. It is a
  `_xact_` lock around a folder insert, so the wait is microseconds.

### What the roles get, and how it is checked

`connect(url, ceiling)` parses the URL, appends the two settings with `Ceiling::applied_to`, and
connects with the result. Appended rather than set, so an operator's own `options=` in
`DATABASE_URL` survives — and since PostgreSQL takes the last `-c` for a setting, ours still wins. A
ceiling somebody can raise from a connection string is not a ceiling.

`ceiling_of(role)` is a function rather than a `match` inlined at the call, so
`a_role_nobody_waits_on_gets_the_long_ceiling_and_the_others_do_not` can assert the mapping without
starting a server. **This is the L2 trap avoided on purpose**: a `pg_sleep` on a `BACKGROUND` pool
proves the numbers, not that `Role::Worker` is handed them.

### A cancelled statement, from the SQLSTATE to the tile

- **`DbError::gave_up()`** — true for `57014` (`statement_timeout`) and `55P03` (`lock_timeout`),
  read off the SQLSTATE inside `DbError::Query`. One place, because every repository method arrives
  the same way through `?`; the four modules that classify a write first (`folders`,
  `saved_filters`, `custom_fields`, `repo`) end in `_ => DbError::Query(err)` and arrive here too,
  so **no other goal's file had to be touched for this to reach every caller**.
- **`client_message()`** grew one arm: a cancelled statement says *"This took longer than the server
  allows and was stopped, so nothing was changed. Something else may be holding the data it needed —
  try again in a moment…"*. Every other `Query` keeps the opaque text. A raw `57014 query_canceled`
  never reaches anybody.
- **`error::log_db_error(err, what)`** — one line, at **warn** when the server stopped it and at
  error otherwise, with the route or widget named. All seven `internal_error` helpers in
  `lapidary-api` log through it (`jobs`, `derive`, `folders`, `blob`, `parts`, `moves`, `download`),
  each keeping its own response shape. Contention should not wake somebody whose alerting watches
  ERROR, and it must still leave a line.
- **The dashboard's key results now tell the two apart.** `value_of` and its seven resolvers return
  `Result<WidgetValue, WidgetRefusal>` instead of `Result<_, String>`: a read the server cancelled
  **is** `timedOut`, not `failed` with a message. Reporting it as `failed` would hide a timeout in
  the wording of a fault, and would make which of the two a locked table produces depend on whose
  clock ran out first.

### The one number that changed: `PER_KEY`, 2 s → 3 s

Not a bigger budget — an **ordered** one. The pool's `lock_timeout` is the two seconds now, and if
the Rust guard were also two seconds, which of them ended a blocked widget would come down to
milliseconds — and ours would usually win, because our clock starts before the statement does. The
key would then be ended by a dropped future, abandoning a running statement, which is the bug. A
second of daylight puts the server first every time and leaves `PER_KEY` for the one thing only it
catches: a key waiting for a **permit or a connection**, where there is no statement to abandon. It
logs a line of its own saying so.

**This was found by mutation, not by reasoning it through first.** `cancelled-widget-reads-as-failed`
survived on the first arrangement: with both ceilings at two seconds the dashboard tests passed
either way, so the test proved nothing about which mechanism stopped the widget. It fails now.

### Measured, on lane 1's PostgreSQL 18 (55433)

| | with the ceiling | without it |
|---|---|---|
| a read blocked on `LOCK TABLE job IN ACCESS EXCLUSIVE MODE`, pool of one | cancelled by the server at **~2.0 s** | cancelled by our clock at 2 s, and the statement kept running |
| the next read on that one connection, lock still held | **8.3 ms** | **2.041 s** (`statement_timeout` alone), and before this goal, *never* — G4's test asserted the connection was unusable until the lock cleared |
| sixteen keys giving up over four rounds — 8 connections, one held by a listener stand-in — worst wait for somebody else's `SELECT 1` | **162 ms** | **2.222 s** |
| `pg_sleep(6)` | cancelled on an `INTERACTIVE` pool, finishes on a `BACKGROUND` one | — |
| twelve blocked keys, four at a time | **6 s** | **3.00 s** with the semaphore removed |

### Tests

- **`crates/lapidary-db/tests/ceilings.rs` (new), 4 tests in 8.0 s.** The role's ceiling as *the
  server* reports it (`current_setting`) and not as our struct spells it, plus an operator's `geqo`
  surviving; **G4's pinned-connection test inverted**; the api's ceiling stopping a statement the
  worker's lets finish, both at once so the file pays six seconds rather than twelve; and a lock wait
  ending sooner than a slow statement, which is what says the two settings are two settings.
- **`crates/lapidary-api/tests/dashboard.rs`, 14 → 15 run.** Its pools now carry `INTERACTIVE`, so
  what ends a blocked widget in a test is what ends it in the api.
  `a_key_that_gave_up_still_holds_its_connection_until_the_lock_clears` is replaced by
  `a_widget_that_timed_out_leaves_the_pool_the_connection_it_was_using` — the same pool of one, the
  opposite assertion. New: `however_many_resolves_meet_a_locked_table_the_pool_still_has_connections`,
  **the test that could not be written before** — four rounds of four blocked keys against eight
  connections with one held for the whole test standing in for `events.rs`'s `PgListener` (G1's
  finding), and a `SELECT 1` looping throughout that has to keep answering in milliseconds. Rounds
  rather than volume, because what the bug did was *accumulate*.
- **Unit tests:** `lapidary-db` — the two SQLSTATEs and nothing else (`40001`, a serialization
  failure, is a real reason to retry and not this one), the caller's message, and the order between
  the two ceilings. `lapidary-api` — `log_db_error` captured through a subscriber: one line, at warn,
  naming the widget, and a real fault still at error. `lapidary-server` — the role mapping, both
  directions.
- **Two of G4's tests were changed, and both are recorded here rather than quietly:**
  - `a_keys_two_seconds_start_when_it_starts_and_not_when_it_was_asked` →
    `a_keys_own_budget_starts_when_it_starts_and_not_when_it_was_asked`, with **eight** blocked keys
    instead of four. The wait the last key survives has to exceed one key's own budget, or a clock
    started at spawn would still have time left when the permit arrived — four blocked keys are a
    two-second wait against a three-second `PER_KEY` and would have let G4's own mutation through.
    Two rounds of four are four seconds and do not.
  - `twelve_blocked_keys_go_four_at_a_time`'s threshold, 3.5 s → **5 s**. Without the semaphore the
    twelve keys used to all give up at two seconds on the pool; now the four that wait get a
    connection when the first eight are cancelled and block for two more, landing at **3.00 s**
    measured. Six against three wants a threshold between them with room on both sides, not one
    0.5 s under the lower number.
  - Both of G4's mutations were re-run against the changed tests and are still caught.

### Decided without the owner

1. **The peer role takes the api's ceiling.** A remote installation is waiting at the other end of
   every statement it runs, its heaviest is one page of a catalogue (`CATALOGUE_MAX`, 500 rows), and
   L2 left "nothing caps how many sharers are worked at once" open for exactly this. The alternative
   was the worker's ceiling, which would have left its pool drainable by one hung statement.
2. **5 s and 2 s rather than something tighter.** A tighter statement ceiling would eventually fail
   a real read on a library larger than anything measured; these are backstops for the api and a
   budget only for the dashboard, which sets its own two seconds anyway.
3. **`PER_KEY` went to three seconds** rather than the dashboard's budget going to one. The
   alternative — `lock_timeout` at 1 s, below an unchanged `PER_KEY` — would have narrowed the
   per-tile budget G4 chose from two seconds to one.
4. **`gave_up()` inspects the sqlx error inside `Query` rather than adding a `DbError` variant.** A
   variant would have needed `_ => DbError::Query(err)` changed in four modules, one of which is
   `repo.rs` — lane 2's file this wave. Reading the SQLSTATE where `client_message` already stands
   reaches every caller and touches nobody else's file.
5. **The status of a cancelled read stays 500.** 503 would read better to a client, and changing the
   status of every route's error path is a wider change than any rule here asks for.
6. **The warn level reaches the seven `internal_error` helpers and stops there.** A handful of
   handlers log a `DbError` outside that family (`tags`, `filters`, `part_number`, `moves`'s rename,
   `blob`'s reachability sweep); a cancelled statement reaching one of those is over-loud, never
   silent, and chasing each was not worth the diff. Said in `log_db_error`'s own doc.
7. **`bin/lapidary-server/src/main.rs` was edited** — one call site and one new function. It is a
   hot shared file whose wave-2 owner (G1) has merged and which wave 3 names no owner for. See the
   note at the top of the hand-back.

### Left for later

- **A key stopped by `statement_timeout` rather than `lock_timeout` still pins its connection for up
  to two seconds past `PER_KEY`.** That is the slow-read path, not the blocked-read path: bounded
  where it used to be open-ended, and no read in `dashboard.rs` has ever measured within an order of
  magnitude of either number. Closing it means the resolve setting its own `statement_timeout` per
  key, which needs the resolvers to hold a connection instead of taking the pool — `repo.rs`'s
  signatures, not this file's. The `ponytail:` on `resolve` says so.
- **sqlx logs its own line for the same statement.** Its default slow-statement threshold is 1 s at
  WARN, and it fires from `QueryLogger::drop`, so every cancelled statement produces sqlx's
  anonymous *"slow statement"* warning carrying the SQL **as well as** ours carrying the widget. Two
  lines that complement each other, so neither was suppressed — and worth knowing that the api was
  never strictly silent here, only anonymous.
- **Nothing measures the ceilings through a running stack.** `pg_stat_activity` on a compose stack
  would show each role's settings; the mapping is unit-tested instead, which is where a mistake would
  actually be made.
- **One more helper to wire, from `main` moving under this goal.** P3 merged an eighth helper of the
  `internal_error` family — `failed(err, what)` in `crates/lapidary-api/src/tags.rs` — which logs at
  error directly. It wants the same one-line change the other seven got,
  `crate::error::log_db_error(err, what)`, and `log_db_error`'s own doc then drops `tags` from the
  list of handlers that stay at error. It is one line in a file this goal never touched, so it is the
  lead's to take at the merge rather than a conflict.
- **`acquire_timeout` is still sqlx's default 30 s on the api's pool.** A caller waiting for a
  connection now waits at most as long as the statements ahead of it, so the default is no longer
  load-bearing — but it is a ceiling nobody chose. The test pools here set 10 s so a starved pool
  fails a test rather than hanging it.
