# L4 — A query that gave up stops running

**Status:** open
**Branch:** `fix/statement-timeouts`
**Wave:** 3 · **Kind:** Rust (small) · **Depends on:** G4 (its test proves the hole) · **Migrations:** —

## Why

Found by G4 while building the dashboard's resolve (2026-09-27), and it is the kind of hole that only shows up when
somebody writes the adversarial test: **a timeout in Rust bounds how long a caller waits, not how long the statement
runs.** Dropping the future cancels nothing on the server, and sqlx cannot return that connection to the pool until
Postgres finishes answering. G4's `a_key_that_gave_up_still_holds_its_connection_until_the_lock_clears` demonstrates it
on a pool of one.

So the resolve route's semaphore bounds how many keys **wait** at once, not how many connections keys that already gave
up are still holding. With a table lock held long enough, repeated resolves can drain a pool of eight and stall
everything else the api serves — the grid, the open path, a download. The dashboard is only where it was noticed;
anything that times out a query has it.

`FEATURES.md` §8 calls per-widget polling a self-inflicted DoS. This is the same shape, one layer down.

## Facts to check before building

- Where the pool is built: `lapidary_db::connect` (`crates/lapidary-db/src/lib.rs`), `max_connections(8)`, and what the
  worker's pool sets differently from the api's — a background job that legitimately runs for minutes must not inherit a
  two-second ceiling.
- **The api now serves on seven of those eight** (found by G1, 2026-09-27): `PgListener::connect_with` calls
  `pool.acquire()` and holds that connection for the life of the process, so the event stream permanently costs one.
  G4's semaphore of four was sized against eight. Not a correctness problem on its own, and it makes this goal's
  arithmetic tighter: four keys that gave up, each still pinning a connection, plus the listener, is five of seven.
- `sqlx::postgres::PgConnectOptions::options` (or `after_connect`) for `statement_timeout` and `lock_timeout`, and
  whether the value belongs on the pool, the role, or the transaction.
- G4's `dashboard.rs`: the 2 s per key starts after its permit, and the queue widget's read is the one the test locks.
- Whether any existing read legitimately exceeds the ceiling this goal picks — the bundle plan, `instance_storage`'s
  disk walk (which G4 already skips), the purge and its recompute, `enqueue_stale_shapes`.

## Rules

- **Server-side, not another Rust timeout.** A second `tokio::time::timeout` would repeat the bug.
- **The api and the worker get different ceilings**, and the difference is stated where it is set. A job that tessellates
  for a minute is not a stuck query.
- An abandoned statement must free its connection *and* say so once, in the api's log, with the widget or route named —
  silence here is what made this invisible until somebody locked a table on purpose.
- The error a caller sees still follows CLAUDE.md: what broke, what to do. A raw `57014 query_canceled` is not that.

## Stages

1. **The ceiling** — `statement_timeout` and `lock_timeout` on the api's pool, chosen against the slowest legitimate
   read, and the worker's pool left long. **Tests:** a statement past the ceiling is cancelled server-side and its
   connection is back in the pool immediately (G4's test, inverted — it should now pass with a pool of one); a worker
   job longer than the api's ceiling still finishes.
2. **The resolve path** — a `timedOut` key no longer pins a connection; twelve keys against a locked table leave the pool
   with eight connections free. **Tests:** repeat G4's lock scenario in a loop and assert the pool never starves — the
   thing that could not be tested before.
3. **Say it once** — the cancelled statement is logged with its route or widget, at warn, without a per-row storm.

## Done when

G4's pinned-connection test passes with the ceiling in place, a locked table cannot starve the pool however many
resolves arrive, a long worker job is unaffected, and `verify slice` is green.
