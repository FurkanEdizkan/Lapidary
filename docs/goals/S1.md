## Why

The api/worker split existed so the `api` image never linked the OCCT kernel. The kernel is gone (R2), both targets
already build from one runtime stage and differ only by `SERVER_FEATURES=worker`, and the jobs crate itself says
ingest takes about 200 ms. Four containers (db, api, worker, Caddy web) for a hobby library is three too many moving
parts; the owner decided on 2026-10-16 that a minimal install is **the app and Postgres**.

  `ceiling_of(role)` (pool size per role), which config fields only one role reads.
- `lapidary_api::Role` and everything it gates in `crates/lapidary-api/src/lib.rs`.

  boundary and die with it, and which guard something still true.
- `scripts/e2e/stack.sh` and `check.sh`: the services they name.

## Rules

- `lapidary-api` stays a library that builds a Router. The static files are mounted by `bin/lapidary-server`.
- The SPA fallback serves `index.html` for unknown non-`/api` paths only; an unknown `/api/*` stays a JSON 404.
- Hashed assets get a long immutable cache; `index.html` never does.
- Opening a page still never loads a model file.
- The peer role keeps working until S3 removes it — leave its arm alone.

### The process

- `LAPIDARY_ROLE` is gone for the app: unset runs the API, the job loop, the hourly quarantine sweep, the
  first-run example seed and the storage-migration check, all in one process. `peer` still selects the sharing
  listener. `api` and `worker` are **refused by name** with a sentence that says to remove the variable and the
  old services, so a pre-S1 compose file fails loudly rather than starting half an application.
- **Two pools, not one.** The API keeps `INTERACTIVE` (5 s statement, 2 s lock); the job loop gets its own pool
  with `BACKGROUND` (10 min, 2 min), so a slow job can never hold a connection a browser is waiting on. That is the
  distinction `ceiling_of(role)` drew, kept without the role.
- **Only `lapidary-api`'s scan route is mounted.** `lapidary-ingest::router` has a second `/scan` (walks inline)
  and `/migrate-storage`; merging it would have panicked on the duplicate route, nothing outside that crate calls
  either, and the boot-time `enqueue_pending_migrations` already covers the second. The router stays in
  `lapidary-ingest` with its own tests — *left for later:* delete it if nothing grows a use for it.
- The `worker` cargo feature is gone; `lapidary-cad`, `lapidary-ingest` and `lapidary-jobs` are plain dependencies
  of the server. `lapidary-api` still may not depend on `lapidary-cad` (`check-layers`), which is the half of the old
  split that ever protected a product rule.

### The browser app

`bin/lapidary-server/src/web.rs`, mounted when `LAPIDARY_WEB_DIR` is set (unset serves the API alone, which is what
`npm run dev` wants). It does what the Caddyfile did: `ServeDir` with an `index.html` fallback for every route the
app owns; `/api` and `/api/*` it does not match stay a bare 404 instead of becoming the front page with a 200; a
missing `/assets/…` file is a 404 too. **Cache rules Caddy never set:** `assets/` is
`public, max-age=31536000, immutable` (Vite hashes those names), everything else `no-cache`. Four tests pin all of
it, and the live stack answered the same on `/`, `/parts/x`, `/api/nope` and a real asset.

**Decided without the owner:** no compression. Caddy gzipped; on a LAN the viewer chunk's 450 kB saving is not worth
tower-http's compression features. A `ponytail:` in `web.rs` says where `CompressionLayer` goes.

### Deploy and the gates

- `deploy/Containerfile` gained a pinned `node:24-trixie` `web` stage (the digest `deploy/web/Containerfile` already
  pinned), lost `ARG SERVER_FEATURES` and the `api`/`worker` targets, and exposes 8080 only. `deploy/web/` is deleted.
- `compose.yaml`: `app` publishes `${LAPIDARY_PORT:-3000}:8080` — the address people already open — and mounts what
  api and worker mounted between them. `LAPIDARY_KERNEL_TIMEOUT` is gone from compose and `.env.example`: nothing
  had read it since R2.
- `check-deploy` keeps the two rules still true — named volumes owned by `lapidary`, and the source-handle
  boundaries in `lapidary-api` and `lapidary-peer` — and now **reports a compose file it cannot parse** instead of
  skipping it (it used `.ok()` there). Kernel-link, role, target, ARG-placement and workflow rules went with the
  split. `xtask/src/strings.rs` lost the eleven fixture exemptions they needed and gained two.
- The Containers workflow builds the one image.
- The rig (`scripts/e2e/`): `app` and `peer`; `API`, `WEB` and `WORKER_URL` are one origin. `check.sh` 80/80.
