## Record

- **compose.**
  - `app` runs with `network_mode: host` and binds its own port. `LAPIDARY_PORT: ${LAPIDARY_PORT:-}` replaces the
    `ports:` mapping and `LAPIDARY_BIND`.
  - `db` is published on `127.0.0.1:${LAPIDARY_DB_PORT:-5439}`, which is where `DATABASE_URL` points.
  - `.env.example` documents both.
- **`bin/lapidary-server/src/ports.rs`.**
  - `first()`:
    - `LAPIDARY_BIND` (a whole address) or `LAPIDARY_PORT` fixes the port, and a busy one fails start-up with a
      sentence;
    - otherwise it takes the saved `instance_setting.port` or 3000, then the first free of the next 20, and remembers
      what it took;
    - it logs "Lapidary is at http://localhost:<port>".
  - `run()` owns every listener. A move binds the new port, saves it, and serves the same Router there. The old
    listener keeps serving for 60 s, is then stopped gracefully, and is aborted 5 s later if an event stream holds it.
  - `GET /api/settings/server` and `PUT /api/settings/port` (admin only; `409` with the deploy/.env sentence when fixed,
    or for a busy port) sit behind `require_user` and `same_origin`, in the binary beside the listeners.
    `lapidary-api` has only the wire types (`server_port.rs`) and still owns no socket.
- **Web.**
  - Settings › Server: the port, editable when not fixed and for an admin. Moving shows `AppSkeleton` over the page
    while `followPort` polls the new origin with a `no-cors` healthz, then goes there on the same path. The cookie
    names no port, so the person arrives signed in.
  - The setup wizard's server step has the port, moved once the account exists.
  - Skeletons (`Skeleton.tsx`: `PartSkeleton`, `TileSkeleton`, `AppSkeleton`, with the existing `GridSkeleton`) replace
    "Loading…" on the part page and dashboard tiles. They are static: motion is for what a person did.
- **Rig.**
  - The override sets `LAPIDARY_PORT` to the lane's web port. `e2e.env` gives the database the lane's spare api
    port (`LAPIDARY_DB_PORT`).
  - `verify_ports` checks that the app is on host networking at the lane port and that the only published port is
    the lane's database.
  - Seed: 17 ok. Flows: 25 ok.
- **Checks.**
  - `ports.rs` tests: a remembered port held by something else is skipped for the next free one, which is remembered;
    a move serves both ports, updates the current port and the setting, and refuses a busy port with its sentence; a
    fixed port is taken as it is and refuses when busy.
  - Live, the binary against the rig's database with no port fixed:
    - it took the saved 31090 and moved to 31095;
    - both answered, and the session worked on the new one;
    - after 67 s the old port was closed and 31095 still answered;
    - the setting read 31095, and port 31000 was refused as "in use by another program".
  - `verify slice`: 14 gates green.
- **Left.**
  - Other tabs on the old port see the connection drop after the minute, with no redirect (`ponytail:` in the plan).
  - Docker Desktop on macOS and Windows needs its host-networking option for this layout.
