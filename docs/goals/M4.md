# M4 — Your folders, read where they are

**Status:** ready, gate log target/verify-M4.log
**Branch:** `feat/index-in-place`
**Wave:** 9 · **Kind:** Rust + deploy · **Depends on:** M3 · **Migrations:** 0062

## Why

Owner, 2026-10-17: do not ingest into a storage location of ours; use each file's own path. A scan
records where a file is and reads it there — **never copies, renames, moves or writes into the owner's
folders** (no `metadata.json`, no `revisions/` directory). Uploads and link imports are written once into
an **inbox folder** the owner chooses, then indexed like any other file.

## Consequences, said up front

- A category is the library's own grouping; moving a part between categories moves nothing on disk.
- A changed file is still a new revision, but only its figures and hash are remembered: the old bytes
  were the owner's file, overwritten by them, and Lapidary keeps no copy.
- Pictures and exports Lapidary makes still live in its own store, which is ours, not the owner's.

## Decisions (lead, 2026-10-17, from the read-only map of the code)

- **Roots.** `library.root`: a path under the ingest mount (`''` = the whole mount for the default library),
  checked with `path_escapes`. A scanned file's `source_path` stays relative to its library's root.
- **Every file row names its root**: a `file.root` column — `library` (the owner's folders, mounted `:ro`),
  `inbox` (Lapidary writes here, once), `store` (rows from before M4, still read from the blob root where they
  are; never moved, never deleted). NULL keeps meaning nothing new.
- **The inbox lives outside the owner's folders** (`LAPIDARY_INBOX_DIR`, mounted rw at `/inbox`): uploads to
  `uploads/<relative path>` (never overwriting — a collision takes a disambiguated name), link imports to
  `imports/<site>/<creator>/<model>/<file>` (Lapidary's own subtree: a re-import may replace its own file, which
  is a new revision), the examples copied in once by the seed.
- **Change detection**: size and mtime recorded at index; a download pre-flights them and refuses with a sentence
  ("this file changed in your folder since Lapidary last read it — scan again") before a byte is sent; the
  end-of-stream hash stays.
- **Revisions without copies**: `file.on_disk`; a changed file is a new revision and the old row is marked not on
  disk. History shows "no longer on disk" instead of a link; the route answers 410. Bundle import records older
  revisions rows-only.
- **Removed outright**: copying into the store, `metadata.json` and `DescribePart`, `revisions/<label>/`,
  `migrate_storage`, moves on disk (a move is a database change), source compression, `SourceWriter`,
  `SourceRelocator`, `IngestBlob`, the reaper's model-file half. Nothing may unlink an owner file; owner roots are
  mounted `:ro` as the backstop.
- **CLAUDE.md** loses "the one before it stays on disk and downloadable" and qualifies "byte-identical" with
  "as long as the file on disk has not changed since it was indexed" (lead edits it at merge).
- **The rig** snapshots the ingest tree before and after scan, move, revision and upload and asserts nothing
  under it changed.

## Done when

Scanning the owner's corpus writes nothing under it; downloads read the original path; the inbox works for
uploads and imports; the rig passes.

### Built

- **Read in place.** `library.root` (a folder under the ingest mount, `''` = the whole mount) and, on
  every `file` row, `root` (`library` | `inbox` | `store`, checked by the schema), `on_disk` and
  `mtime_ns` — migration `0062`, which also marks every existing row `store`, drops `quarantined_file`
  and fails any still-queued `ingest_blob` / `migrate_storage` / `describe_part` job with a sentence.
  A scan walks the library's folder and records each file's path under the mount; ingest reads it
  through `LibraryReader` (no method that writes, renames or removes) with the size and mtime of the
  handle it read, and writes nothing anywhere. A re-scan of unchanged bytes refreshes the recorded
  mtime, so a `touch` never leaves a file undownloadable.
- **Storage crate rebuilt around three handles.** `LibraryReader` (read-only, any root, legacy zstd
  decode by the recorded level), `InboxWriter` (the only writer of source files: never over an
  existing upload — `name (2).stl` — and replace-if-changed for Lapidary's own `imports/` and
  `examples/`), `DerivativeStore` (+ `put_file` for imported bundles), and `Roots`. `SourceStore`,
  `SourceWriter`, `SourceRelocator`, `WorkerRole` and source compression are gone.
- **Downloads** read the row's root; a pre-flight compares size and mtime and refuses a change with
  409 "This file changed in your folder since Lapidary last read it — scan again." (inbox: "upload or
  import it again"), a missing file with 409 naming the path, a revision whose file was replaced with
  410. The end-of-stream hash stays and its truncation message now speaks per root. Bundles skip
  revisions no longer on disk and pre-flight the rest.
- **Revisions without copies.** `record_revision` writes the new row at the file's place and marks
  every earlier row at the same root and path `on_disk = false`; nothing is set aside. History shows
  "No longer on disk" instead of a link. A bundle import writes each revision into the inbox at
  `imports/bundles/<source path>` in turn, so the older ones end as rows and the newest as the file.
- **Moves are database-only.** `move_to_folder(part, from, to)`; the route no longer refuses
  "migration pending", and every card is draggable.
- **Inbox.** `LAPIDARY_INBOX_DIR` (required; the server refuses to start with it inside the ingest
  dir, on container or host paths). Uploads: the commit checks every staged file is there, copies
  each into `uploads/<path>` hashing as it copies, and queues the new `ingest_inbox` job; the probe's
  `needRows` and the upload's "already stored" line are gone. Link imports: `imports/<site>/…`. Seed:
  `examples/…`. Compose bind-mounts `${LAPIDARY_INBOX_DIR:-../inbox}:/inbox:z` and passes
  `LAPIDARY_HOST_INGEST_ROOT` / `LAPIDARY_HOST_INBOX_ROOT`.
- **Removed outright:** `migrate_storage` (job, route, startup enqueue, db module, 2,000+ lines of

### Decided without the owner

- **A row's location is `root` + `storage_path`**, `storage_path` relative to the directory the root
  names; for a scanned file that is `library.root` joined with `source_path`, so downloads and exports
  need no library lookup and a library's root can be read once per job.
- **`file.root` is NOT NULL** after `0062` backfills `store`; there is no fourth meaning for NULL.
- **A new job kind, `ingest_inbox {path, source_path}`**, replaces `ingest_blob`, rather than a root
  on `ingest_file` — so queued `ingest_file` rows still parse unchanged. Its `path` key is the part's
  source path (what a failure is listed under); `inbox` is where the file is.
- **mtime is stored as integer nanoseconds** (`mtime_ns bigint`), taken from the open handle's
  metadata, never a `timestamptz`.
- **Bundle imports land at `imports/bundles/<source path>`**; each revision is written there in turn,
  so older ones end `on_disk = false`. A bundle **export** leaves out revisions no longer on disk.
- **An upload that replaces a part's file under another inbox name** leaves the earlier inbox file
  `on_disk = true` and downloadable — nothing replaced it.
- **`InboxWriter::put` skips an identical file**, so a re-import of unchanged bytes keeps its mtime.
- **`0062` drops `quarantined_file`** and nothing unlinks the files its last rows named; they stay.
- **The instance storage figure counts store rows only**; the per-library total counts every file
  still on disk ("in your folders").
- **Create-library takes an optional `root`** (API only, refused if it escapes); no UI field.
- **Store rows keep `on_disk = true`** even when a later revision of the part is a library file:
  those bytes are Lapidary's and are still there.
- **Compose's inbox is a bind mount** (`../inbox` default, gitignored), owned by 10001 as the store is.
