# A33 — A rescan queues only what changed

**Status:** merged
**Branch:** `perf/scan-diff`
**Wave:** 16 · **Kind:** ingest + db · **Depends on:** A32 · **Migrations:** 0070

## Why

Owner, 2026-10-20, "do the fixes" (the scale report's fix plan, items 1 and 8). An unchanged rescan of 20,299 files takes
85 s: every file still becomes a job, and each job is a dequeue, one revision lookup and an update. Each scan also adds
one more `failed` row for every file it refuses, so the dashboard's failed count climbs with every scan.

## Decisions

- **The walk compares before it queues.** One query reads the library's current source files (path, size, mtime, the same
  "current" the per-job skip uses); each found file is stat'ed with the same `stat_at` the job uses; one predicate
  decides "unchanged" for both. Unchanged files are not queued. The per-job skip stays as the safety net.
- **They are still counted.** The scan job's row keeps how many files it found unchanged (`job.unchanged`, 0070), and
  `batch_status` adds them to `total` and `skipped`, so "Scan complete — 0 added, 20,299 already here" stays true.
- No "seen" update: nothing reads one; the per-job skip never wrote one either.
- **An older refusal goes when a newer scan has tried the same file:** a failed `ingest_file` row is pruned once a later
  batch holds a job for the same path.

## Done when

An unchanged 20k rescan finishes in under 5 s and adds no file job rows; failed rows stay one per refused file; gate and
rig pass.
