# M3 — Delete is delete

**Status:** ready, gate log target/verify-M3.log
**Branch:** `chore/delete-is-final`
**Wave:** 8 · **Kind:** Rust + web · **Depends on:** M1 · **Migrations:** 0061

## Why

Owner, 2026-10-17: "we don't want a restore option; if it is deleted it is deleted." Delete removes a
part from the library immediately — its rows, pictures and tags — and **never touches the file on disk**
(M4 makes the library read your folders in place). Restore, purge, the removed list, soft delete and the
30-day quarantine go. CLAUDE.md's "delete is soft" rule is rewritten with the owner's words.

## Done when

One Delete, behind a confirmation that says the file stays; no removed list, restore or purge anywhere;
nothing reads `deleted_at`.

## Record

**Built.**
- **db.** `PgParts::delete(part) -> bool` replaces `soft_delete`, `restore` and `purge`. It locks
  the row, then runs one shared helper, `repo::delete_parts`. The helper deletes child-first:
  `part_image`, `part_source`, `derivative`, `file`, `revision`, `part_move`, `part`.
- **What delete recounts, and what it writes.**
  - It recounts only derivative hashes.
  - It writes **no `quarantined_file` row and no source-hash recount**, so nothing ever queues a
    model file for the reaper.
  - `PurgeReport`/`Purged` and the `Shows` enum are gone, and so are all `deleted_at` reads.
  - Facet, page, search and sorted queries were renumbered.
  - `removed_bytes` is gone from `StorageTotals`/`InstanceStorage`, and `removed_at` from
    `PartSummary`.
  - The `deleted` flag is gone from `CurrentRevision`.
  - `OptionInUse` loses `removed`.
- **Folder delete.** `PgFolders::delete_subtree` replaces `soft_delete_subtree`.
  - It deletes every part in the subtree through the same helper.
  - It deletes `part_move` rows whose `from_folder`/`to_folder` is in the subtree. A part moved
    *out* of the folder survives; its trail entry does not.
  - It then deletes the folders in one statement (`NO ACTION` FKs are checked at statement end).
- **Migration `0061_delete_is_final.sql`.** It hard-deletes every soft-deleted part and folder,
  together with each removed folder's whole subtree and the parts filed in it. It works
  child-first, includes `part_move`, recounts derivative blobs the `0055` way, then drops
  `deleted_at` on `part` and `folder`.
- **api.**
  - `DELETE /api/parts/{id}` answers 204, then 404 on a repeat.
  - The `restore` and `purge` routes are gone, and so is the `PurgeResult` binding.
  - `?state=removed` is gone from parts and facets. An old `state=` is simply ignored.
  - Folder delete answers `foldersDeleted`/`partsDeleted`.
- **ingest.**
  - A re-scan of a deleted part's file ingests it as a new part.
  - The seeder now records its run (see decisions).
- **web.**
  - The `/removed` route and the restore/purge client calls are gone.
  - There is one shared `ConfirmDelete` dialog, built on `Dialog`. Cancel is focused first. It is
    used by the part page and by the grid selection bar. The body says “The file itself stays
    where it is on disk.”
  - The visible "Remove" is now "Delete".
  - Folder-delete wording says deleted, not hidden, and that files stay.
  - `removedBytes` is gone from the storage panel and the dashboard widget.
- **e2e.** A `delete` flow replaces remove-restore. It uploads its own stamped part, deletes it
  through the dialog, checks the "stays on disk" sentence, and expects a 404 from
  `GET /api/parts/{id}` afterwards.
- **Docs.**
  - The rule in CLAUDE.md and PRODUCT.md is now in the owner's words, and AGENTS.md was
    re-exported.
  - DATA.md §1.6 is now "Deletion is one step". The quarantine text is kept for cache eviction.
  - The `deleted_at` line is gone from the schema listing.

**Tests added.**
- **db**
  - `deleting_a_part_queues_nothing_for_removal_and_leaves_no_row_behind`: no `quarantined_file`,
    no source-blob clock, no rows, and a second delete returns `false`.
  - `deleting_a_part_takes_its_bytes_off_the_library_panel`.
  - `deleting_a_folder_keeps_a_part_moved_out_of_it`.
  - The folder cascade test now checks that the rows are gone.
  - `removed_parts_and_folders_are_deleted_and_the_column_goes`: a `0061` test, run up to `0060`
    by hand.
- **api**
  - `deleting_a_part_never_touches_its_model_file`: a real storage root, and the file is byte-equal
    after `DELETE`.
  - Every read path returns 404 after delete, and the restore and purge routes are gone.
  - Deleting one of two parts that share a blob leaves the other part whole.
- **ingest**
  - `a_deleted_parts_model_file_survives_every_sweep_and_only_its_export_leaves`: delete, then a
    sweep at zero retention. The export leaves and the model file stays byte-equal.
  - `deleting_a_revised_part_leaves_every_file_and_directory_in_place`.
  - `a_re_scan_re_ingests_a_deleted_part_as_a_new_one`. This inverts the old "deleted stays
    deleted" test.
- **Mutation checks.** Each restore was verified by copy and sha256.
  - Dropping the seed record made `deleting_every_seeded_part_does_not_bring_them_back` fail on
    its own assertion.
  - Making `delete_parts` recount file hashes as well made
    `deleting_a_part_queues_nothing_for_removal_and_leaves_no_row_behind` fail.

**Decided without the owner.**
- **The seeder writes a history row.** `seed_examples` never wrote a `job` row. What used to stop
  a re-seed after the examples were deleted was the hash short-circuit over soft-deleted rows, and
  hard delete removed it. Without a fix, a restart after deleting every example would bring them
  all back.
  - The fix is `PgJobs::record_seeded`. After a seed that added parts, it writes one finished
    `scan_directory` row, in a batch of its own.
  - It is `done`, so no worker claims it and no queue count shows it. No status route reaches its
    batch.
- **The source blob's `ref_count` is left as it was.** A deleted part's source blob keeps its
  count, now above the true number, and is never quarantined. Recounting it is what used to let
  the reaper unlink the model's bytes.
  - The cost is that an un-migrated (content-addressed) source copy is never reclaimed after
    delete.
  - Gallery-image blobs are not recounted either, as before.
- **The legacy queue still drains.** The reaper keeps its `quarantined_file` path half. Nothing
  writes that table any more, but it still drains files a purge queued before 2026-10-17, which
  the owner had explicitly asked for at the time.
  - `0061` leaves existing `quarantined_file` rows alone.
  - The reaper tests now write that legacy queue by hand (`retire`).
- **A move trail naming a deleted folder is deleted, not set to NULL.** NULL would read as "the
  library root", which would be false.
- **The web lane's own calls.**
  - Both confirmation bodies also say "this cannot be undone".
  - The folder-delete dialog says the same.
  - `scripts/e2e/check.sh`'s list of strings the flows depend on was updated to `Delete` plus the
    "stays on disk" sentence. That was outside the brief, but check.sh needed it to pass. `Delete`
    matches almost anything in strings.ts, so that entry guards very little.
  - The e2e `delete` flow runs only at 1440 wide; the old flow also ran at 390.
  - Each e2e run leaves its uploaded file on the test stack's disk, by design.

**The M4 edge case.** A deleted part's model directory stays on disk untouched, and nothing
records it. `model_dir_for` disambiguates against a directory that exists, so a re-scan of the
same file, or of new bytes at that path, files a **second copy** beside it, in
`<model>_<6 hex>/`. The old directory keeps a `metadata.json` naming a part id that no longer
exists.
- Nothing is overwritten.
- `a_re_scan_re_ingests_a_deleted_part_as_a_new_one` pins this.
- M4, which reads the library's folders in place, ends the copy.
