## Why

Four recorded gaps in the peer protocol, one of them a safety ceiling.

## Facts checked (as of `3964524`)

- **The ceiling** (ROADMAP "Shared folders with several holders", and `0044_relayed_catalogue.sql`): whether a folder
  may be passed on is decided by the roster its owner published, readable only from that owner; an owner who takes
  somebody off and goes offline leaves other holders serving them. `peer_share_member.seen_at` says how old the answer
  is; nothing refuses an old one. Owner's decision (2026-09-21): **7 days**.
- **A waiting pull holds the others:** `crates/lapidary-peer/src/pull.rs:254` `ponytail:` — one pull at a time in
  all; upgrade named there: pulls per sharer.
- **Staging is never cleared** after a failed pull (ROADMAP S4 "left for later"; no cleanup code in
  `crates/lapidary-peer/src`).
- **The puller's page does not say a share asks first** before pulling (S4 "left for later"): the peer list's `Share`
  wire type carries no mode.

## Rules

- Owns: `crates/lapidary-peer/src/{pull,sync,shares}.rs`, `crates/lapidary-db/src/{mirror,pulls}.rs`,
  `bin/lapidary-server/tests/peer_*.rs`, migration `0052`, and the asks-first note on

- Wire changes are additive with `#[serde(default)]`: an older installation reads the new field as absent. Never bump

## Stages

1. **Roster cutoff** — `ROSTER_TRUSTED_FOR = 7 days` in `lapidary-db::mirror`; `relayable_to`, `relayed_to` and
   `serves` require `peer_share_member.seen_at` within it. **Tests:** an 8-day-old roster is neither relayed nor
   served; a fresh read restores both. Close the ROADMAP ceiling and `0044`'s comment.
2. **Pulls per sharer** — the peer role runs one pull per sharer concurrently instead of one in all (the in-flight
   limits on the sending side are unchanged). **Test:** a pull waiting on A's grant does not hold a pull from B.
   Remove the `ponytail:`.
3. **Staging cleanup** — a pull that finishes failed or is stopped removes its staged files that no unfinished pull
   still wants. **Test:** after a failed pull, staging is empty; a second pull of the same files still resumes from
   what it needs.
4. **Asks first, before pulling** — `Share.asks_first` on the wire (`serde(default)`), `peer_share.asks_first`
   (`0052`), `MirroredShare.asksFirst`, a line on the shared folder's page. **Tests:** an older list without the field
   reads as open; the page says so when it is set.
5. Mutation checks: the cutoff removed; pulls back to one in all; cleanup deleting a file another pull wants.

## Record

### Stage 1 — the roster stops being an answer after 7 days (done)

`ROSTER_TRUSTED_FOR_SECS = 7 * 24 * 60 * 60` in `lapidary-db::mirror`, beside the types it governs, and
`relayable_to`, `relayed_to` and `serves` each require `peer_share_member.seen_at` inside it. **The ceiling
`0044` recorded is closed** — see "left for the lead" for the ROADMAP lines, which a lane may not write.

- **Named `ROSTER_TRUSTED_FOR_SECS`, not `ROSTER_TRUSTED_FOR`,** after its sibling `ONLINE_WITHIN_SECS`: both are
  seconds bound into `make_interval(secs => $n::float8)` and compared on the database's clock, which is the one
  clock the api and the peer role share. It is **not re-exported from `lib.rs`** — that is L4's file, and nothing
  outside `mirror.rs` needs the number.
- **In `serves` the age goes inside the `LEFT JOIN`'s `ON`**, not beside it, so a roster row too old reads exactly
  as no roster row does: `Serving::NotShared`, the refusal a stranger gets. Telling those two apart would say
  that this installation once held a list with the caller on it.
- `0052` adds `peer_share_member (device_id, seen_at)`: all three reads now ask for that folder's row for that
  device *recently enough*, and the index carries what they ask by.
- **The stated test would have passed on a cutoff of one day**, so it does not only check 8 days: it walks
  *fresh → 6 days → 8 days → fresh* and asserts all three reads at each step. The 6-day step is what pins the
  owner's 7 days rather than any cutoff at all, and `cutoff-of-one-day` is the mutation that proves it. Said here
  as G1 did: **the stage's test was changed.**
- Nothing expires in the table. `seen_at` only moves forward, and the reads are what refuse a stale row — so the
  pages that list a folder's people, its introductions and what was declined read exactly as before, and a week
  of an owner's silence costs the people in their folder the relay, not their history.

### Stage 2 — one pull at a time per sharer, the sharers beside each other (done)

`pull::run` is now `sync::run`'s shape: `PgPulls::sharers_waiting()`, a `tokio::spawn` per sharer guarded by a
`HashSet<DeviceId>` of who has one running, and each task working `PgPulls::next_of(sharer)` until there is
nothing of theirs left or one of theirs stalls. The `ponytail:` at `pull.rs:254` is gone. The in-flight limits on
the **sending** side are untouched; this is only about who this installation asks, and when.

- **`queued_behind` is per sharer now.** It counted every unfinished pull started before this one; with the
  sharers running beside each other that number tells a person to wait for something that is not in their way.
  One `AND q.device_id = pu.device_id`, and the mutation that replaces it with `AND TRUE` fails the stage's own
  test on the number it reads (1, not 0).
- **The stated test cannot be written against `work`.** `work(A)` then `work(B)` passes on the old scheduler, and
  survives the "one pull in all" mutation. It drives `pull::run` with a shutdown token instead: Ayşe's Terrain
  asks first and is asked for **first**, so the old scheduler would take it, be told to wait, and never reach
  Burak's — and the test asserts Burak's pull reaches `done` while Ayşe's is still `waiting`. **The stage's test
  was changed**, for the same reason as stage 1's.
- `peer_pull.rs` grew a **second sharer** on the one database the file already shares: Burak, his own identity,
  his own store, his own peer service and his own folder (Bases, one hex base). The mesh generator is
  parameterised so his folder's file is a **different** file — two sharers offering the same bytes is exactly the
  staging collision below, and a test should not be the thing that finds it.

### Stage 2's other half — a real bug the concurrency opened, fixed here

Staging is keyed by the file's **hash** and shared by every pull. With one pull at a time that was safe. With two
sharers' pulls running beside each other, two folders holding the same file — two people in one hobby scene very
often do — would have had one fetch truncating `<hash>.part` while the other appended to it, and the loser's
BLAKE3 check would have failed and **told the person the sharer's store needs checking** for a file that was
never wrong. Or one fetch would have renamed to `<hash>` while the other was still appending to that inode, and
`fetch`'s whole-file short-circuit would have handed back the half-written file unchecked.

So a fetch **claims** `<staging>/<hash>` while it stages it, and the second fetch stalls — which is the state that
already means "try again shortly". Keyed by the whole path rather than by the hash, because two staging volumes
are two files: one peer role has one, and this crate's own `tests/fetch.rs` stands three side by side and all three
ask for the same hash. That is how the path key was found — by two of those three failing on the hash key, not by
reasoning about it. Asked **after** the whole-file check, so the ordinary case — a
file already staged and wanted by both — costs nothing and stalls nobody.

### Stage 3 — staging holds only what some unfinished pull still wants (done)

`PgPulls::staged_wanted()` is every BLAKE3 an unfinished pull wants, `paused` included because pausing promises
that what is staged stays; `pull::sweep` removes every staging entry that is a hash, or a hash and `.part`, and is
not in it. Anything else in that directory was not put there by a fetch, and a sweep is no place to guess.

- **It hangs off `work`, not off the five places a pull can finish.** `work` is now a wrapper: `attempt`, then
  sweep, then the attempt's own outcome. What the sweep asks is not "how did this one end" but "what does anybody
  still want", so it is right after every attempt: a pull that stalled is unfinished, so its files stay and its
  next attempt resumes from them; a pull that failed, or whose folder is gone, has no claim on anything. One
  query, one call, and it covers a pull failed by a path nobody has written yet.
- **A bug that predates this goal, deleted rather than fixed.** After queueing its bundles, `work` removed each
  file it had staged — including files a *second* pull of the same folder into a second library was resuming
  from. The loop is gone; the sweep is what takes them, and the existing test that staging is empty once the
  import is queued still passes through it.
- `staged_wanted` is a **superset on purpose**: it does not ask which of those files the destination library
  already holds. Keeping a file a pull turns out not to need costs a staging volume nothing for a round; the
  other way round deletes what a pull is resuming from.
- The stated test would have passed on today's code with nothing staged, since `Refused` already drops its own
  partial. It stages half a cliff face first, starts **two** pulls of that folder into two libraries, **pauses
  the second**, fails the first by removing its sharer, and asserts the partial is still 1024 bytes — then
  resumes the second, finishes it, and asserts staging is empty. **The stage's test was changed**, and the pause
  was added because the mutation that drops `paused` from the wanted states survived without it.

### Stage 4 — asks first, before pulling (done)

`Share.asks_first` with `#[serde(default)]` (`false` — open, which is what every folder was before asking first
existed), `peer_share.asks_first` (`0052`), through `OfferedRemote`, `RelayedShare`, `MirroredShareRow` and
`MirroredShare.asksFirst` to one line on the shared folder's page. `PROTOCOL` is untouched.

- **A hint, never authorization**, said in `0052`, on the wire type and on the api type. What decides is the
  owner's own answer to `POST /peer/v1/shares/{share}/request`, and the roster's `may_fetch` for the other
  holders. A copy of this column that is behind costs a sentence and never a file.
- **Only a folder's owner may change it.** `take_offer` upserts it as
  `CASE WHEN peer_share.device_id = $7 THEN EXCLUDED.asks_first ELSE peer_share.asks_first END`: a member
  relaying the folder may **seed** it on a folder this installation is hearing of for the first time, and may
  never change it afterwards. Without that, a member running a build from before the field sends none, which
  reads as open, and would turn an ask-first folder open again on **every hello round** — the page line would
  flicker. Decided without the owner; the alternative was last-writer-wins.
- **L1's half was not re-fixed.** The gap it found was in `web/src/lib/api.ts`'s `shareCategory`, and
  `PgShares::requests` filtering `s.mode = 'ask'` and deleting nothing is left exactly as it merged.

### Decided without the owner

- **7 days is `ROSTER_TRUSTED_FOR_SECS`, in seconds and not re-exported**, for the reasons above.
- **A stale roster reads as `NotShared`, not as a third answer.** Telling "too old" apart from "never on it"
  would say that this installation once held a list with the caller on it.
- **A relayed offer may seed `asks_first` and may not change it.** Last-writer-wins would have flickered the page
  line on every round against a member from before the field.
- **`queued_behind` is per sharer.** It is a shipped number on a shipped screen; with the sharers running beside
  each other the old one was simply wrong.
- **The post-import staged-file delete was removed rather than narrowed.** The sweep already answers the question
  it was trying to answer, and answers it for a second pull of the same folder too.
- **The staging claim was added, although no stage asked for it.** Stage 2 makes it a live data-corruption path,
  and the error it would have produced blames the sharer.
- **`0044`'s comment was not edited.** sqlx records a checksum per applied migration and refuses a file that
  changed, so editing it would break every existing installation's next start. `0052`'s comment closes it by
  name instead, and says which reads now refuse a stale roster.
- **The `sharing` strings block gained one string** (`libraryAsksFirst`). L1 owns that block and has merged, and
  no other wave-3 goal touches it.
- **`main` was not merged.** `git rev-parse main` is still `82eabbd`, the commit this branch was cut from.

### Left for later — one line each, for the lead to file

- **The ROADMAP's two "known ceiling" paragraphs are now closed** — `docs/ROADMAP.md` around lines 3232 and 3323,
  both saying "it wants a staleness window on `peer_share_member.seen_at`, and is not built". It is built:
  `ROSTER_TRUSTED_FOR_SECS`, 7 days, in `relayable_to`, `relayed_to` and `serves`. A lane may not edit that file.
- **A bundle zip can be left in staging for ever.** `pull-<id>-<n>.zip` is written and deleted inside one
  blocking closure, so a crash between the two leaks up to 64 MB. The sweep deliberately does not touch it: it
  only knows names that are a hash. Keyed on the pull id it would be a few lines, and it is not what this goal's
  stage asked for.
- **Nothing caps how many sharers are worked at once.** The peer role's pool is `max_connections(8)`
  (`lapidary_db::connect`) and two of those are held for good by its own listeners — `sync::run`'s and
  `pull::run`'s. The pull tasks take a connection per query and hold none across network I/O, so ten sharers is
  not ten held connections; but a statement that hangs would pin one, which is exactly the shape **L4** is open
  for. Not measured, and deliberately not fixed here: a cap belongs with server-side `statement_timeout`.
- **A pull stalled by another pull's claim waits a whole hello round** (`ROUND`, 15 s) for a file that may finish
  in a second. Correct, and not quick. A notification when a claim is released would remove the wait.
- **`peer_share.asks_first` is never cleared when a folder stops being offered and comes back relayed only.** The
  row is deleted with the folder when its owner stops offering it, so the case needs an owner who stops offering,
  a member who keeps relaying, and the owner never returning — at which point the stale hint outlives nothing
  that can correct it. Noted, not built.
