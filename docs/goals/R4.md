# R4 — Purge the rendered derivatives

**Status:** ready at 857d4d1, gate log target/verify-R4.log
**Branch:** `chore/purge-renders`
**Wave:** 5 · **Kind:** Rust + ops · **Depends on:** R3 · **Migrations:** 0055

## Why

Every thumbnail, rung, structure, entity and PMI row in the database is now unreadable and unrebuildable:
nothing produces them and, with the kernel gone, nothing could. The owner asked for the space back.

**After R3, not before.** Purging while a producer can still write is a race that re-fills what you emptied.

## Facts checked (2026-10-03, `73c4836`)

- **`free_render_cache` is the wrong vehicle.** It is 90-day-age-gated, user-triggered, and deliberately
  excludes L0 and thumbnails (`repo.rs:3051-3056`). Bending it to purge unconditionally would destroy the
  behaviour the "free cache space" button promises — and that button's wording is a product rule: eviction
  must never read as data loss.
- **`PgBlobs::reap` is the only code in the workspace that unlinks a blob**, and the only code carrying the
  foreign-key decline and the unlink-before-commit ordering that makes a concurrent re-ingest of the same
  bytes safe (`repo.rs:655-700`). A migration cannot unlink files at all.
- `recount` (`repo.rs:1158-1181`) counts `file` **and** `derivative` references. The `file` half is the whole
  guard against quarantining a blob a source file still needs.

## Rules

- Derivatives are **our** data, not the user's, so the 30-day hold is not owed to them — the quarantine path
  is used because it is the only safe unlink, not out of ceremony. Say so where the code says it.
- A blob a `file` row still references is **untouched**. Copy `recount`'s predicate; do not retype it.

## Stages

1. **Migration 0055** — delete every `thumbnail`, `tessellation_*`, `structure`, `entities`, `pmi` and
   `export_*` row, then inline `recount`'s predicate over the affected hashes so an orphan lands at
   `ref_count = 0` with `quarantined_at = now()`. The hourly reaper unlinks them later with no new code.
   **Exports are the one judgement call here, and R3 changed its terms.** R3 deliberately left the kernel
   version string **unchanged**, because `enqueue_stale_derivatives` compares it against every stored export
   row — bumping it would re-queue every export in the corpus at the next worker start. So deleting the
   export rows is not free the way this goal first assumed: each one deleted is one a person re-earns by
   asking for it again. Decide it on that basis and say which way you went — the renders have no such
   question, since nothing can rebuild them at all.
   **Tests:** seed a thumbnail, an L0 and a blob shared with a `file` row; afterwards the rows are gone, the
   orphan is quarantined with `ref_count = 0`, and **the shared blob is untouched and un-quarantined**.
2. **What the panel says** — `render_cache_bytes` and `inline_preview_bytes` now read zero. `Storage.tsx`
   says why rather than showing a dead row, and "free cache space" keeps working over exports alone.

## Recorded, not built

- **Inline thumbnails are `bytea`**, so deleting rows returns no disk until `VACUUM FULL derivative`, which
  cannot run inside a migration's transaction. It is a post-deploy command for the Record, with the bytes
  measured before and after.
- **Getting the disk back sooner than 30 days needs new code.** Never run the reaper's sweep at retention 0 —
  the same sweep collects user source files purged yesterday, and `QUARANTINE` is deliberately not
  configurable.

## Record

**Done.** `derivative` holds only what something can still build. Migration `0055` deleted every
`thumbnail`, `tessellation_l0/l1/l2`, `structure`, `entities` and `pmi` row and handed their blobs to
the existing reaper; **the `export_*` rows stay** (below). `inlinePreviewBytes` leaves the panel and
the wire, and three of the cache strings stop promising a render.

### The exports stay, and that is the one thing decided alone

R4.md's stage 1 listed `export_*` among the rows to delete and R3 corrected its terms. Checked
rather than assumed: **deleting an export re-queues nothing.** `enqueue_stale_derivatives`
(`jobs.rs:387`) selects `FROM derivative`, so it only re-queues a row that *exists* with a stale
`kernel_version` — a missing export is never swept, and the corpus-wide re-queue R3 avoided by
leaving the version string alone cannot be triggered from this side either. So the cost of deleting
one is exactly what R3 said and no more: a person re-earns it by asking again.

Kept anyway, for three reasons that all point the same way:

1. **The Done-when line decides it.** "The derivative table holds only what something can still
   build" — an export *is* what something can still build. The rule `0055` leaves behind is that
   invariant, and the predicate is written as `kind NOT IN ('export_stl', 'export_3mf')` so it says
   so rather than listing seven kinds somebody later has to keep in step.
2. **There is already a path for evicting one**, and its promise is the product rule. An
   unconditional sweep of rebuildable rows, from a migration, with no age gate and nobody pressing
   anything, is "free cache space" without the thing that makes its wording honest.
3. **The owner asked for the space back, and the exports are not where it is.** Every unrebuildable
   row went; what is left is cache with a button on it.

### Migration 0055, and the trap in the obvious shape of it

Two statements, and **it cannot be one.** Every sub-statement of a query sees the same snapshot, so
a data-modifying CTE's deletions are invisible to the counting subqueries beside it. Measured
before the migration was written: folded into one statement, the recount reads the four rows it has
just deleted, the orphan comes back at `ref_count = 4`, **nothing is quarantined at all**, and the
migration reports success. A temporary table is what puts the delete in the past before the count is
taken; it is the mutation `count-taken-before-the-delete` below.

1. `CREATE TEMP TABLE purged_render_blob (h text PRIMARY KEY)`.
2. `WITH doomed AS (DELETE … RETURNING blake3) INSERT INTO purged_render_blob SELECT DISTINCT …
   WHERE blake3 IS NOT NULL` — `DISTINCT` because a part whose L0, L1 and L2 encoded to one blob is
   three rows and one hash; `IS NOT NULL` is the inline thumbnail, whose bytes are the row.
3. **`recount` (`repo.rs:1071`), copied and not retyped** — the same statement with
   `unnest($1::text[]) AS h` changed to the temporary table and nothing else touched.
4. `DROP TABLE purged_render_blob`.

**It unlinks nothing, and that is the design.** `PgBlobs::reap` is the only code in the workspace
that unlinks a blob and the only code carrying the unlink-before-commit ordering and the
foreign-key decline; a migration cannot unlink a file at all. So `0055` marks and the hourly sweep
collects, with no new code. Written in the header where the code says it: these derivatives are
**ours**, so the thirty-day hold is not owed to anybody — the quarantine path is used because it is
the only *safe* unlink, not out of ceremony.

### The bytes

**No real corpus was measured**: the owner's installation is not this lane's to touch and its
database was not up. Two numbers instead, both labelled.

**Measured end to end on a 500-part fixture** (a throwaway database, all 55 migrations, 500 inline
thumbnails of 20,480 incompressible bytes and 500 hash-addressed L0s of 204,800 bytes):

| | `pg_total_relation_size('derivative')` | blobs quarantined |
|---|---|---|
| before | 11,739,136 | — |
| after the migration | **11,739,136** | 500 / **102,400,000 bytes** |
| after `VACUUM FULL derivative` | **32,768** | 500 / 102,400,000 bytes |

So on that fixture the migration accounts for **114,139,136 bytes**: 11,706,368 of them come back
the moment `VACUUM FULL` runs, and 102,400,000 wait out the thirty days and then the hourly reaper.
**The delete on its own returns nothing** — the table was the same size afterwards to the byte.

**The queries to take the real figure with**, before the deploy and either side of the vacuum:

```sql
-- what is in the table, by kind
SELECT kind, count(*) AS row_count, count(blake3) AS hash_addressed
  FROM derivative GROUP BY kind ORDER BY kind;
-- the hash-addressed bytes 0055 hands to the reaper
SELECT count(*) AS blobs, coalesce(sum(b.stored_bytes), 0) AS bytes FROM blob b
 WHERE EXISTS (SELECT 1 FROM derivative d
                WHERE d.blake3 = b.blake3 AND d.kind NOT IN ('export_stl', 'export_3mf'))
   AND NOT EXISTS (SELECT 1 FROM derivative d
                    WHERE d.blake3 = b.blake3 AND d.kind IN ('export_stl', 'export_3mf'))
   AND NOT EXISTS (SELECT 1 FROM file f WHERE f.blake3 = b.blake3);
-- the bytes it does NOT free, because a file row or an export still names them
SELECT count(*) AS blobs, coalesce(sum(b.stored_bytes), 0) AS bytes FROM blob b
 WHERE EXISTS (SELECT 1 FROM derivative d
                WHERE d.blake3 = b.blake3 AND d.kind NOT IN ('export_stl', 'export_3mf'))
   AND (EXISTS (SELECT 1 FROM file f WHERE f.blake3 = b.blake3)
     OR EXISTS (SELECT 1 FROM derivative d
                 WHERE d.blake3 = b.blake3 AND d.kind IN ('export_stl', 'export_3mf')));
-- the inline thumbnails, which only VACUUM FULL returns
SELECT count(*) AS row_count, coalesce(sum(octet_length(thumb_bytes)), 0) AS bytes
  FROM derivative WHERE thumb_bytes IS NOT NULL;
-- the table on disk; run again after VACUUM FULL derivative
SELECT pg_total_relation_size('derivative') AS bytes;
```

### Recorded, not built — the two ops facts, confirmed

- **`VACUUM FULL derivative` is a post-deploy command**, not part of the migration: it cannot run
  inside a transaction, and it takes an `ACCESS EXCLUSIVE` lock, so export reads and writes wait
  while it runs. Measured above: without it the delete returns no disk at all.
- **Never run the reaper's sweep at retention 0** to get the hash-addressed half sooner. The same
  sweep collects the user's own source files purged yesterday, and `QUARANTINE` is deliberately not
  configurable. Getting it sooner needs new code.

### What the panel says

- **`inline_preview_bytes` is gone** from `InstanceStorage`, `InstanceStorageView`, the bindings,
  `Storage.tsx`, the dashboard widget and `strings.storage.everything`. It read
  `derivative.thumb_bytes`, `0055` deleted every row of it and `upsert_derivative` writes the column
  `NULL`, so it could only ever report zero — and the string printed it unconditionally, so every
  installation would have read "0 B of thumbnails in the database" for ever. The two dead
  `octet_length(d.thumb_bytes)` summands in `storage_totals` went with it, for the same reason: `+ 0`
  over every library, in a figure somebody will one day have to check.
- **`render_cache_bytes` does *not* read zero, and stage 2's premise was wrong about that.** R3 had
  already narrowed `cache_kinds` to the exports, which are live; the figure is non-zero the moment
  somebody's export goes 90 days unread. There is no dead row to explain, so nothing explains one.
- **The words had to follow R3, not R4.** `renderCache` said "detailed 3D previews", `freeCacheBody`
  promised a part would "open at once on its coarse preview while the detailed one is rebuilt", and
  `cacheFreed` said "render cache" — all three described a rebuild nothing can perform. They say
  slicer files now. The wire names (`renderCacheBytes`, `POST /api/storage/render-cache`) are
  unchanged.
- **The quarantine clause no longer says "purged".** It read `N purged and waiting out its 30 days`,
  which was true while a purge was the only thing that put bytes there. After `0055` the figure on
  every upgraded installation is mostly what *Lapidary* deleted, and telling somebody who has purged
  nothing that their store holds purged data is exactly the data-loss reading `CLAUDE.md` forbids
  here. It names the hold and what ends it: `N on hold for 30 days before the space comes back`.
- `RenderCacheFreed::rungs` → `removed`. The wire already said `removed`; the field was the last
  place in that path still counting rungs.

### Tests

`the_renders_leave_the_table_and_only_their_own_blobs_are_quarantined`, run with

**Four blob stories, because the predicate has four outcomes and only one case reaches each** —
this is what the two `predicate-drops-…` mutations below prove, each caught by exactly one of them:

| seeded | expected | what it holds open |
|---|---|---|
| named by four dead rows and nothing else | `(0, quarantined)` | the sweep gets it, and only after the delete is visible |
| named by a dead row **and a `file` row** | `(1, not quarantined)` | **the whole guard**: a live model file |
| named by a dead row **and a surviving export** | `(1, not quarantined)` | the `derivative` half |
| named by an export alone | `(1, not quarantined)` | its hash never reaches the recount — a drifted counter is left drifted, not corrected in passing |

Plus an inline thumbnail (`blake3 IS NULL`, no blob to settle), and **a row of kind `preview`, which
no build has ever written**: it is what makes `NOT IN (the two exports)` a decision rather than a
spelling, and it is the only thing `migration-names-the-seven-instead` can fail on.

### Mutation check

`target/mutate-r4.sh` (`migration|cache|all`), logs in `target/mutations-r4/`. **Six mutations, six
caught**, every failure message read and matched to the case it was supposed to reach.

| mutation | caught by, and what it said |
|---|---|
| `predicate-drops-the-file-half` | the shared-with-a-file case alone: `(0, true)` for `(1, false)` — a live model file's bytes quarantined |
| `predicate-drops-the-derivative-half` | the shared-with-an-export case alone, same shape |
| `count-taken-before-the-delete` | the orphan: `(4, false)` for `(0, true)` — the snapshot trap, exactly as measured |
| `migration-takes-the-exports-too` | `[]` for `["export_3mf", "export_stl"]` |
| `migration-names-the-seven-instead` | `["export_3mf", "export_stl", "preview"]` |
| `cache-stops-asking-what-kind-a-row-is` | `only_old_exports_are_cache_and_an_unrebuildable_rung_is_left_alone`: 3 rows evicted, not 2 |

**The first version of the last one SURVIVED, and the reason is worth more than the mutation.** It
widened `d.kind = ANY($1)` alone, and nothing changed: a row of an unrebuildable kind is itself an
`o` that `free_render_cache`'s `NOT EXISTS (… AND NOT o.kind = ANY($1))` finds on its own blob, so
the second clause declines it whatever the first one matches. **Two clauses name a kind there and
the second is the guard** — dropping either alone changes nothing, which is precisely how both come
to be dropped by somebody tidying up. The mutation now replaces both, and the finding is written
into the SQL where it was found.

**One mutation was not written, rather than counted.** `coalesce(b.quarantined_at, now())` — the
clause that stops the migration restarting a clock that is already running — has no case in this
test that can reach it: a blob with `quarantined_at` set *and* a dead derivative row pointing at it
cannot be produced by any path in this build, because every writer of that column counts derivative
rows before setting it. The clause is `recount`'s own, copied verbatim, and `recount`'s purge tests
are where it is held. Breaking it here would also be the *safe* direction — a restarted clock delays
a reap. Written down rather than padded into the table.

### Decided without the owner

1. **The exports stay** — above, with the three reasons and the sweep behaviour that was checked
   rather than assumed.
2. **`kind NOT IN (the two exports)`, not `IN (the seven)`.** Nine kind strings have ever existed
   (`git log -p` over `derivative.rs`; the one spelling bug, `export3mf`, was in the serde name and
   the job payload, never in `derivative.kind`). The negative predicate states the invariant the
   table keeps afterwards, and it settles a row of a kind nobody thought to list — which is
   unrebuildable by definition, since no build can name it.
3. **`thumb_bytes` and `derivative_storage_is_exclusive` are left in place.** Dropping the column
   would need the constraint restated and would return no space without the same `VACUUM FULL` the
   deleted rows need anyway: risk without a byte to show for it.
4. **`inline_preview_bytes` deleted rather than left reading zero**, with the two dead
   `octet_length` summands in `storage_totals` — above.
5. **Four cache strings reworded.** Three of them were already false after R3; the fourth, the
   "purged" clause, becomes misleading *because* of `0055`.

### Two findings for the lead, neither fixed here

- **`recount` does not count `part_image`, and `reap` does not either. Latent, with no reachable
  path found — checked, not assumed.** `part_image.blake3` references `blob` (`0015`), and both
  `recount` (`repo.rs:1074`) and `PgBlobs::reap`'s `DELETE` count `file` and `derivative` alone. If
  a blob a `part_image` row names were ever quarantined, the reaper's delete would be refused by
  `part_image_blake3_fkey` rather than declined by its own `NOT EXISTS`, and because the sweep is
  one transaction **the whole hourly sweep would roll back, every hour, for ever** — the
  availability failure `reap`'s own doc is written around. Nothing is lost; quarantine stops
  collecting. What was checked, and why nothing reaches it:
  - **`0055` cannot**: nothing has ever written a `part_image` row from a render. `origin =
    'rendered'` is in `part_image_known_origin` and has no producer in `src/`, and no migration or
    `backfill/` file inserts a `part_image` row at all — so no blob a dead derivative named is also
    a gallery picture, and this migration's hash set is the dead rows' alone.
  - **`purge` cannot**, which is the thing worth writing down: it deletes a part's `part_image` rows
    but its `doomed` set (`repo.rs:2142`) is the part's `file` and `derivative` hashes only, so a
    picture's hash never reaches `recount`. Two parts sharing one picture are safe today for that
    reason and not by design — and "a purge of one of two parts sharing a picture" would pass as a
    test against the current code.
  - **Nothing else deletes a `part_image` row.** `DELETE FROM part_image` appears once in `src/`,
    in `purge`. There is no remove-one-picture path yet; `add_part_image` increments `ref_count` and
    clears the flag, and nothing decrements. So a gallery blob is never reaped — disk kept, not
    lost.
  So the hole is a trap for the next person rather than a bug today: the gallery is the one
  reference class the quarantine machinery does not know about, and the first route that removes a
  picture, or any widening of `purge`'s `doomed` set, lands in it. It wants the third term in
  `recount`, in `purge`'s `doomed` set and in `reap`'s predicate, together with the remove-a-picture
  route that would be its first caller. The predicate here was copied verbatim as R4.md's rule says,
  with the omission named in the migration header where it stood.
- **A shared part now has no picture at all.** R3 recorded this as coming; it has arrived.
  `PgShares::catalogue` and `PgShares::thumbnail` (`shares.rs:595,647`) read `kind = 'thumbnail'` as
  a SQL literal, and after `0055` there is nothing to read. Nothing breaks — `catalogue`'s is a
  `LEFT JOIN LATERAL`, so the part is still listed with `thumbnail: false`, and the route answers
  404 rather than 500 — but the shared-library page is pictureless, and `strings.parts.thumbnailAlt`
  survives for a page that will never have an image to describe. Shares should mirror `part_image`.
