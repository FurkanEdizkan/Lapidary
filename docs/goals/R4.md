# R4 — Purge the rendered derivatives

**Status:** open
**Branch:** `chore/purge-renders`
**Wave:** 5 · **Kind:** Rust + ops · **Depends on:** R3 · **Migrations:** 0055

## Why

Every thumbnail, rung, structure, entity and PMI row in the database is now unreadable and unrebuildable:
nothing produces them and, with the kernel gone, nothing could. The owner asked for the space back.

**After R3, not before.** Purging while a producer can still write is a race that re-fills what you emptied.

## Facts checked (2026-10-03, `73c4836`)

- **`free_render_cache` is the wrong vehicle.** It is 90-day-age-gated, user-triggered, and deliberately
  excludes L0 and thumbnails (`repo.rs:3051-3056`). Bending it to purge unconditionally would destroy the
  behaviour the "free cache space" button promises — and that button's wording is a product rule: eviction
  must never read as data loss.
- **`PgBlobs::reap` is the only code in the workspace that unlinks a blob**, and the only code carrying the
  foreign-key decline and the unlink-before-commit ordering that makes a concurrent re-ingest of the same
  bytes safe (`repo.rs:655-700`). A migration cannot unlink files at all.
- `recount` (`repo.rs:1158-1181`) counts `file` **and** `derivative` references. The `file` half is the whole
  guard against quarantining a blob a source file still needs.

## Rules

- Derivatives are **our** data, not the user's, so the 30-day hold is not owed to them — the quarantine path
  is used because it is the only safe unlink, not out of ceremony. Say so where the code says it.
- A blob a `file` row still references is **untouched**. Copy `recount`'s predicate; do not retype it.

## Stages

1. **Migration 0055** — delete every `thumbnail`, `tessellation_*`, `structure`, `entities`, `pmi` and
   `export_*` row, then inline `recount`'s predicate over the affected hashes so an orphan lands at
   `ref_count = 0` with `quarantined_at = now()`. The hourly reaper unlinks them later with no new code.
   Exports go too: they are rebuildable on demand, and emptying them means R3's kernel-version change finds
   nothing stale on first boot.
   **Tests:** seed a thumbnail, an L0 and a blob shared with a `file` row; afterwards the rows are gone, the
   orphan is quarantined with `ref_count = 0`, and **the shared blob is untouched and un-quarantined**.
2. **What the panel says** — `render_cache_bytes` and `inline_preview_bytes` now read zero. `Storage.tsx`
   says why rather than showing a dead row, and "free cache space" keeps working over exports alone.

## Recorded, not built

- **Inline thumbnails are `bytea`**, so deleting rows returns no disk until `VACUUM FULL derivative`, which
  cannot run inside a migration's transaction. It is a post-deploy command for the Record, with the bytes
  measured before and after.
- **Getting the disk back sooner than 30 days needs new code.** Never run the reaper's sweep at retention 0 —
  the same sweep collects user source files purged yesterday, and `QUARANTINE` is deliberately not
  configurable.

## Done when

`verify slice` green, the derivative table holds only what something can still build, and the Record names
the bytes reclaimed and the bytes still waiting on the quarantine.
