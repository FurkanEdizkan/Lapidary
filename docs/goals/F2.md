# F2 — A stable file link

**Status:** ready, gate log target/verify-F2.log
**Branch:** `feat/stable-file-link`
**Wave:** 7 · **Kind:** Rust + web · **Depends on:** S4 · **Migrations:** —

## Why

A download today is `GET /api/revisions/{id}/download?variant=original`, keyed by revision, so a copied link goes
stale the moment a new file is recorded. People want one link per part that always gives the current file — to paste
into a slicer, a chat, a script.

## Facts to check before building

- `crates/lapidary-api/src/download.rs` (1,147 lines): headers it sets, whether it already answers `Range`, how it
  hashes on the way out, how it names the file.
- How "the part's current revision" is read today (the part page shows one).

## Rules

- `GET /api/parts/{id}/file` serves the current revision's **original** bytes through the same code path as
  `variant=original` — never a conversion.
- `Content-Disposition: attachment; filename*=UTF-8''<original name>`. Range answers 206 with a correct
  `Content-Range`; a range on a hash-checked stream is allowed to skip the outgoing hash check for that request, and
  the code says so.
- Access is what it is today: whoever reaches the port. FEATURES.md says it in those words.

## Stages

1. The route. **Tests:** full body byte-identical (BLAKE3) to the ingested file; `Range: bytes=0-99` gives 206 and
   100 bytes; after a new revision the same URL gives the new file.
2. "Copy link" on the part page and the card menu. **Tests:** web test.

## Done when

`curl -r 0-99` and a full `curl | b3sum` both check out against a real stack.

## Record

**Done.** `GET /api/parts/{id}/file` is one link per part that always gives its current file.

- **The route** looks up the part's newest revision (`PgParts::latest_revision`, already there) and serves
  it through the same code as `variant=original`, now one function, `serve_original`: same headers,
  strong `ETag`, outgoing BLAKE3 check, touch. A deleted part or an unknown id is a 404 whose sentence says
  to copy the link again from the part.
- **Range, on both routes**, because it is the same code: one `bytes=` range (`a-b`, `a-`, `-n`) is 206
  with `Content-Range`; past the end is 416 with `bytes */size`; several ranges or another unit get the
  whole file (RFC 9110 allows it). **`If-Range` that is not this file's `ETag` gets the whole file** — the
  file behind `/parts/{id}/file` changes when a revision is recorded, and resuming the old one onto the new
  one would splice two files. A range skips the outgoing hash (the digest covers the whole file), and the
  code says so; stored bytes may be a zstd frame, so the start is read through, not sought. Every full
  answer now says `Accept-Ranges: bytes`.
- **Copy link** on the part page and in the quick look, beside Download. **The fallback is the point:**
  `navigator.clipboard` exists only in a secure context, and a LAN install is plain `http://`, where it is
  undefined — so without the clipboard the link is shown, selected, to copy by hand. The card has no
  download control since R1, so it got no copy action either.

**Tests:** three route tests (whole and byte-identical, `0-99`, resume under `If-Range`, suffix, a stale
`If-Range`, 416, the revision route's range; the link following a second revision while the first stays
downloadable; deleted and unknown ids). Mutation: disabling the `If-Range` rule fails the first. One web
test for both clipboard branches. 422 of 422 web tests.

**Measured on a real stack:** `curl` of a seeded spur gear's link: 200, 61,684 B, `Accept-Ranges: bytes`,
and the body's BLAKE3 equal to the `ETag` and the ingested hash; `curl -r 0-99`: 206, `bytes 0-99/61684`,
100 B.

**Access**, as the owner decided for a local install: whoever can reach the port.
