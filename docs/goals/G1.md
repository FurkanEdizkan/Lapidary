Postgres listener per browser tab was rejected in `crates/lapidary-api/src/jobs.rs`. This goal gives the app one

## Stages

1. `0049`: `lapidary_changed()` → `pg_notify('lapidary_events', library_id::text)` after insert/update/delete on
   `part` (per row) and after `UPDATE OF state` on `job` when the new state is `done` or `failed`.
2. One `PgListener` per api process; the hub groups per library over 250 ms, sends `AppEvent::Changed` on a
   `broadcast`; `Lagged` or a listener reconnect becomes `Resync`; the hub ends on shutdown and so do the streams.
3. `GET /api/events` (`events::router(hub)`, api role), `X-Accel-Buffering: no` and `Cache-Control: no-cache` there
   and on the batch stream.
4. **Tests** (`crates/lapidary-api/tests/events.rs`): one part insert in library A gives `changed{A}` within 1 s; 100
   inserts in one transaction give exactly one event; two subscribers and still one `LISTEN` backend in
   `pg_stat_activity`; the headers; a lagging subscriber gets `resync`; shutdown ends the stream; a job reaching
   `done` notifies.
5. **Measured through containers** (lane port block): `curl -N -H 'Accept-Encoding: gzip' <web>/api/events` shows
   `changed` within 1 s of an upload finishing; five tabs, one LISTEN backend. Docker: this goal may start compose
   projects named `lapidary-lane<n>-*` from the existing `lapidary-check-*` images (tagged per project); no builds.

### The migration, and why it is a trigger

`0049_change_events.sql`: `lapidary_changed()`, `pg_notify('lapidary_events', library_id::text)`, on
`part` after insert/update/delete per row and on `job` after `UPDATE OF state` when the new state is
`done` or `failed`. `OLD.library_id` on a delete, `NEW` otherwise. **No constraint on `job` is
restated** — `0047`'s `job_outcome_known`, `profiled` and all, is untouched.

The comment says what the stage list asked it to say, and the reason is worth repeating here because
it is the one design decision in this goal that is not local: every other channel in this repository
is notified by the statement that causes it, and that is right for those, because each has exactly one
writer. "Something in this library changed" has many — ingest, upload, a folder move, a rename, remove,
restore, purge, a revision, a fold, and every job that ends — and a `pg_notify` per writer is a line
each of them has to remember. The first one that forgets is a page that silently stops updating for
that one kind of change, which is the worst shape of bug this application can have because it looks
like nothing at all. Two things come free with the trigger and would have had to be earned otherwise:
it fires inside the writing transaction, so a rolled-back change notifies nobody, and PostgreSQL
delivers one notification per distinct (channel, payload) per transaction, so a transaction touching
four hundred parts of one library wakes a page once.

### Db and api

- `crates/lapidary-db/src/events.rs`: `CHANGE_CHANNEL` and `listen_for_changes(&PgPool) -> PgListener`.
  A free function rather than a `Pg…` struct — it has no other statement to keep company. There is
  deliberately no `pg_notify` call in the file: the trigger is the writer.
- `crates/lapidary-api/src/events.rs`: `Hub`, `Hub::spawn(db, shutdown)`, `router(hub)`, and
  `no_buffering()`. `WINDOW` 250 ms, `BACKLOG` 256, `RETRY` 5 s.
- **`Hub::spawn` is `async` and opens the first listener before it returns** (not in the stage text).
  Opening it inside the task races the caller's next write: a change made immediately after startup
  would be notified into a channel nobody is listening on yet. The `listener-opened-late` mutation
  below is what holds this.
- **`Hub` holds a `broadcast::Receiver`, not the `Sender`**, and clones itself with `resubscribe()`.
  This is the whole shutdown story and it replaces the "thread a second cancellation signal through
  the router" shape: the hub task owns the only sender, so its return on shutdown closes the channel,
  and every open stream ends by itself. `resubscribe` also starts a new tab at the current tail, so a
  page that opens now is not handed events from before it asked.
- **`try_recv`, never `recv`.** They differ in exactly the thing this stream cares about. Both
  reconnect; `recv` does it silently, so the notifications that arrived while the connection was down
  are simply gone and every page is left showing something untrue with nothing saying so. `try_recv`
  reports the reconnect as `Ok(None)`, which is what makes `Resync` possible at all. Checked against
  sqlx 0.9's source rather than assumed, including that `recv_unchecked` is written to be cancel-safe
  (`connection/stream.rs:80`: "NOTE: to not break everything, this should be cancel-safe"), which is
  what lets the grouping timer and the listener share one `select!`.
- The grouping timer is a free-running `tokio::time::interval`, not a window opened by the first
  notification. Same 250 ms ceiling, half the average latency, three fewer lines, and no `Sleep` to
  reset. Its cost is a 4 Hz wake in an idle api process, which is less than the batch stream already
  spends per open tab.
- A payload that is not a library id is logged and **dropped**, not fanned out as a resync: only
  `0049`'s trigger should ever write this channel, and a stranger on it must not be able to make every
  tab re-fetch.
- `GET /api/events` is `events::router(hub)`, merged in `bin/lapidary-server/src/main.rs` in the
  `Role::Api` arm alone. `X-Accel-Buffering: no` and `Cache-Control: no-cache` there **and** on
  `jobs.rs`'s per-batch stream, from the one `no_buffering()` they share. axum's `Sse` already sets
  `Cache-Control`; `IntoResponseParts` *inserts* rather than appends, so it is written once either way,
  and the header test asserts exactly one of each.
- `tokio-stream` gains `sync`, for `BroadcastStream` — the one dependency change this goal's Owns list
  names. `lapidary-api` also gains `tokio-util`, which it does not; see "Decided without the owner".

### Tests: 9 in `crates/lapidary-api/tests/events.rs`, 2 unit

The integration tests write raw SQL, which is unusual for this crate. What is under test is a
*trigger* — a rule the database enforces on every writer there is and every writer there will be — so
going through one repository would narrow the claim to that repository, and would make a hundred rows
a hundred ingests. The whole file runs in **3.42 s**.

The header test builds the router **`bin/lapidary-server` actually serves** — `lapidary_api::router`
merged with `events::router` — rather than the events router alone, because that merge is the one seam
nothing else covers: axum panics at merge time on a path both routers claim or a fallback both set,
and the first place that would otherwise show is a container that will not start.

A part insert within a second; a rename and a delete; a hundred inserts in one transaction as one
event; ten separate transactions in each of two libraries grouped per library; five open streams and
one LISTEN backend; a job silent on `pending → running` and notifying on `done` and on `failed`; a
terminated LISTEN backend becoming `resync` and then listening again; both streams' headers; shutdown
ending every open stream and the ones opened after it.

Two of these are worth naming, because the stage list's version of them would have passed on broken
code. **"100 inserts in one transaction give exactly one event" does not test grouping** — PostgreSQL
collapses that case by itself, so the test passes with the hub's window deleted. The test that holds
grouping is the added one: ten *separate* transactions per library, asserted against a ceiling **timed
from the burst itself** — one event per window the burst spanned, plus the boundaries at either end —
rather than a fixed two. Twenty round trips to a PostgreSQL every lane shares can outlast one window on
a busy machine, and a fixed two would go red for the load rather than for the code. Measured here the
burst is 103 ms, so the ceiling is 2; the 1 ms-window mutant gives 10 either way, which was rechecked
against the timed version. And **"a lagging subscriber gets resync" is a
unit test**, on the `resolve` function the route reaches through `frame`, plus one that overflows a
real `broadcast` to confirm which error that raises — rather than an integration test that would have
had to spend 256 windows of wall time to overflow the production buffer.

**Which arm the reconnect took, since both are possible.** The terminated backend came back as
`try_recv`'s `Ok(None)`, not as an `Err` followed by the 5 s `RETRY`: the whole nine-test file finishes in
under 3.5 s, so no test in it can have waited out a five-second retry. So the measured path is sqlx
noticing the connection go and re-establishing it immediately, which is the path the design counts on;
the retry loop is the one nothing here exercises.

`stop()` in that file does double duty: it asserts the hub gives its connection back, and it is what
lets `#[sqlx::test]` tear its database down. `pool.close()` waits for every connection to come home,
and a `PgListener` holds a pooled one for as long as it is listening.

### Decided without the owner

- `Hub` holding a `Receiver` rather than a `Sender`, so that shutdown propagates by channel closure
  instead of by a second signal.
- `Hub::spawn` being `async`, for the startup race above.
- `BACKLOG = 256`. The buffer is per channel and one flush sends one event per library that changed, so
  the number that matters is how many libraries can change inside one window. 256 is far past any real
  installation and costs 256 pointer-sized slots for the process's life.
- A free-running `interval` for the window rather than a timer armed by the first notification.
- **`lapidary-api` gains `tokio-util`**, which the Owns list does not name — only `tokio-stream`'s
  `sync` feature. It is `CancellationToken` and nothing else: the signal `bin/lapidary-server` already
  holds and that `lapidary-jobs`, `lapidary-ingest` and `lapidary-peer` already take, and it is already
  linked into this crate's binaries through `lapidary-jobs`, so it adds no compile or supply-chain
  surface. The alternative was making `Hub::spawn` generic over `impl Future`, which buys nothing here.
- Raw SQL in the integration tests, for the reason above.
- One line added to `crates/lapidary-api/src/lib.rs`: `pub mod events;`. Declaration only — the route
  chain, which G4 was in this wave, is untouched.
- ARCHITECTURE's proxy paragraph now says there is **no separate `/events` path**: both streams live
  under `/api`, so the one Caddy rule covers them. It also records that Caddy's `reverse_proxy` flushes
  whether its `encode gzip zstd` holds an event stream anyway is **not yet measured**, and names stage 5
  as what measures it. I first wrote that Caddy flushes an event stream without being told to, which is
  true of `reverse_proxy` as far as I can read it and is exactly what stage 5 exists to confirm — so it
  had no business being stated in ARCHITECTURE before anybody had seen it.

### Two things G5 should know before it wires refetch-on-changed

Checked here because this goal is what makes them possible, and neither is visible from the web side.

- **There is no refetch loop, and I confirmed it rather than assuming it.** The `part` trigger fires on
  every `UPDATE part`, so a GET handler that stamped a part row would make opening a page notify every
  tab, whose refetch would stamp again, forever. Every `UPDATE part` in `lapidary-db` is on a write path
  (custom fields, fold, soft delete, restore, part number, tags, materials, move, folder delete, and the
  measurement copy inside a revision write); the api's only GET-side write is `Touches`, which is
  `UPDATE blob SET last_accessed_at` and never touches `part`.
- **A `changed` event can be the consequence of the browser's own POST.** The on-demand derive routes
  (`/thumbnail`, `/rungs/{level}`, `/exports/{format}`) enqueue jobs, and a job reaching `done` **or
  `failed`** is an event. So refetch-on-changed must not re-POST a derive it already asked for — a
  failed derive would otherwise be retried on its own failure notification, in a loop.
