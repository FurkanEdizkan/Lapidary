# A30 — A grid that holds twenty thousand parts

**Status:** merged
**Branch:** `perf/windowed-grid`
**Wave:** 15 · **Kind:** api + web · **Depends on:** A29 · **Migrations:** —

## Why

Owner, 2026-10-18: "lets investigate optimization and how we handle thousands of models", then "do 1 and 2 first".
Measured on a check stack of 20,336 parts from the owner's corpus: the server answers a grid page in 3–9 ms, but the
browser holds every card it has scrolled past — 13,250 cards after four minutes, 834 MB of heap and 300,000 DOM nodes,
each next page slower than the last (2,000 cards took 16 s at the start and 58 s by 12,000) — and a 60-card page is
0.7–3.8 MB, because each card's picture rides inline as a `data:` URL.

## Decisions

- **Pictures by address.** A card's picture is `/api/parts/{id}/images/{imageId}` (an inline one, served from its row)
  or `/api/blob/{hash}` (a stored one), never a `data:` URL; the grid's query no longer reads the bytes. The new route
  is behind `auth::scope` like every part route and cached `private, immutable`: an image id's bytes never change.
- **Only the rows on screen are in the DOM.** The grid measures one row and its columns, renders the rows in view plus
  a margin, and stands the rest in as padding above and below, so the scrollbar is the whole library's. The pages
  already fetched stay in memory (a card without its picture is a few hundred bytes). Without layout (tests) it renders
  everything, as before.

## Done when

Scrolling the 20k check library to its end stays steady per page and holds a bounded DOM and heap; a grid page is tens
of kB; every card still shows its picture; gate and rig pass.

## Record

The check stack (lane 1): the owner's corpus plus 50 hard-linked copies of its 371 small meshes, 20,336 parts.
Before → after on this branch:
- **A 60-card page:** 0.7–3.8 MB → 45 kB (200 cards: 2.4 MB → 167 kB); 2–9 ms either way.
- **Scrolling to ~13k cards loaded:** heap 834 MB and 300k DOM nodes → 34–200 MB with 78 cards drawn; smooth-scroll frames
  p50 16.7 ms at 1k, 5k and 13k (a 33 ms p50 sample at 10k).
- **Still open:** a page takes longer to land the more are loaded (about 0.45 s at 1k, 1.35 s at 7.5k, measured by
  jumping to the end over and over, which unmounts and remounts the whole window each time); a steady scroll with the
  two-screen prefetch rarely meets it.
- Every picture shows, stored ones included. The check stack first ran against the checkout's `storage/` (compose's
  fallback); its 24 blobs were moved out, unreferenced, and it now has its own store.
Rig 29/29 (grid flows now count loaded parts from the count line and expect picture addresses), gate 14/14. Shots in
`/mnt/Storage2/lapidary-a30-shots`.
