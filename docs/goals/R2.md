# R2 — OCCT out, STEP and IGES refused by name

**Status:** ready at e23312f, gate log target/verify-R2.log
**Branch:** `chore/remove-occt`
**Wave:** 4 · **Kind:** Rust + deploy · **Depends on:** — · **Migrations:** —

## Why

The owner's call (2026-10-03): the CAD kernel goes. With no rendering and no measurement of B-rep files,
OCCT's remaining purpose was format conversion for a format the library will no longer take. It is the
single most expensive thing in the repository: **766 s of an 849 s cold build** is OCCT compiling itself, its
test image is **2.92 GB**, and it puts **74 MB across 148 files** into the worker image.

A worker without the feature already refuses STEP and IGES — but it refuses them by telling the operator to
rebuild with `--features occt-kernel`, which will be a lie. The refusal has to become the truth: this
library indexes meshes.

## Facts checked (2026-10-03, `73c4836`)

- Only `lapidary-cad` links it, behind `occt-kernel`, re-exported by `bin/lapidary-server`. Nothing links
  OCCT's C++ directly — `OcctKernel` runs `occt-bridge` as a subprocess, so a crash fails one job.
- `deploy/Containerfile` stages: `occt` (builds OCCT V8.0.1 from source, sha256-pinned) and `occt-test`.
  `api` deliberately carries none; `worker` copies `/opt/occt/lib` and sets `LD_LIBRARY_PATH`.
- `xtask` carries gates that exist only for this: `Tier::Occt` in `verify.rs`, and `ApiTargetCarriesOcct`,
  `WorkerTargetMissingOcct`, `OCCT_STAGE`, `KERNEL_LINKED_SERVICES` and the `SERVER_FEATURES` rule set in
  `deploy.rs`.
- `kernel_for` (`handler.rs:309`) routes `step`/`iges`/`igs` to the CAD kernel and errors otherwise.
- `CAD_FORMATS` is chained into `is_model_file` (`lapidary-core/src/part.rs:227`). **Leave it there** —
  drop it and a scan *silently skips* a `.step` file, which is not "refused with a clear message".

## Rules

- **One commit.** `check-deploy` cross-reads `Containerfile`, both compose files and
  `.github/workflows/containers.yml`. Remove a stage without its rule and the gate fails mid-stage, blocking
  every lane behind it.
- The refusal follows CLAUDE.md: what broke and what to do. It names the format and says what this library
  takes — never "rebuild with a feature" that no longer exists.
- Do not touch the render pipeline: that is R3's, and the two goals share `handler.rs` and `derive.rs`.

## Stages

1. **The sidecar and the feature** — delete `sidecar/occt-bridge/`, `lapidary-cad/src/occt.rs`,
   `tests/occt_bridge.rs`, and the `occt-kernel` feature from all three manifests.
2. **The deployment** — the `occt` and `occt-test` stages, the worker's OCCT copy and `LD_LIBRARY_PATH`,
   `SERVER_FEATURES` in compose and the containers workflow; then `Tier::Occt` and `check-deploy`'s four
   OCCT rules with their unit tests.
   **Tests:** `check-deploy` green; the `worker` image builds with no OCCT layer and starts.
3. **The refusal** — `kernel_for` refuses CAD formats unconditionally with the new sentence; `upload.rs`
   refuses them up front with the same sentence rather than letting a per-file job fail later.
   **Tests:** the existing STEP cases in `tests/handler.rs` flip polarity — a STEP file is refused by name,
   permanently, and ingests no part; a scan reports it rather than skipping it silently.

## Done when

`verify slice` green (13 gates once `Tier::Occt` goes), the worker image builds and starts without OCCT, and
a `.step` file is refused in words a person can act on. **Record the before/after worker image size and cold
build time** — this goal's whole point is what it gives back.

**Why the "after" is a bound and not a number.** After this goal the `worker` image *is* the `api`
image's layers plus one binary layer — no stage adds anything else — so its content is
`api − api's binary + worker's binary` = 97,806,924 − 17,086,608 + *W*. Only code was removed, so
*W* ≈ the 19,631,248 B worker binary goal 8 built, so the figure above is a close bound and the
saving is essentially the full 77,404,618 B of OCCT. (The kernel-less binary built *here* came out
at 20,078,160 B — larger, not smaller. That is the host toolchain and linker against the trixie
image's, not a regression; the two are not comparable, which is the whole reason the "after" row is
derived from the api image rather than from a local build.) The three before-figures check out exactly: the
worker-minus-api content gap is 79,949,258 B = 77,171,690 + 232,928 + 2,544,640.

**What was not weighed, and the one decision it leaves.** Building the `worker` image to put it on
the scale needs the pinned `rust:1.95-trixie` (not on this machine, ~1.3 GB compressed) plus a
release build layer, against **8.4 GB free on `/`** and an 8 GB floor. So R2.md's "the worker image
builds and starts without OCCT" is **half met**: the kernel-less release binary was built here and
*does* start as a worker, logging `kernel=mesh, for stl, obj and 3mf` and bringing its job loop up
against a scratch database. The image build itself is the lead's, on the next container run.

**There was nothing left to delete.** No `lapidary-occt:*` or `occt-test` image is on this machine
and `docker buildx du` holds no OCCT cache record — goal 9's prune already took them. This goal's
saving is every future build, not reclaimed disk.

### The refusal

One sentence, in `lapidary_core::cad_refusal` (`crates/lapidary-core/src/part.rs`), because two
places refuse and a person who meets both must meet the same words:

> Lapidary is a visual library of meshes and does not read STEP files. Export the part as STL,
> OBJ or 3MF from your CAD tool and add it again; the same file is refused the same way every time.

- **`kernel_for`** (`lapidary-ingest/src/handler.rs`) refuses `CAD_FORMATS` unconditionally and
  `Permanent`, whatever kernel the handler holds. It used to say "rebuild the worker with
  `--features occt-kernel`", which after this goal would send somebody to a flag that does not exist.
- **`upload.rs`** refuses in **`probe` and `commit`**, and only when the manifest **holds no mesh
  at all**. The probe is the point — it runs before a byte is transferred, so a folder of STEP
  assemblies is refused rather than moved and then failed a job at a time. The commit checks again
  because the probe is a courtesy a client can skip. A manifest with a mesh in it is taken, and any
  B-rep file in it is refused by its own job with this same sentence — see below.
- **`bin/lapidary`'s folder agent leaves B-rep files out of its manifest** and says `cad_refusal`
  once per path. Not silently: a file an owner put in a watched folder that never appears and never
  explains itself is the same bug as a scan skipping one.
- **`CAD_FORMATS` stays chained into `is_model_file`**, as the goal file required. Two tests hold
  it there: one in `part.rs` on the predicate, one in `tests/handler.rs` that walks a directory
  holding a `.step` file and asserts the scan *reports* it and the job *refuses* it. Dropping the
  chain makes a scan skip the file in silence, which is the failure this repository keeps finding.

**Where the upload guard fires is the hardest thing in this goal, and two wrong shapes passed
their tests on the way here.** Both are written into `refuse_b_rep`'s doc comment so the next
person to tidy it reads why first.

1. *Refuse a manifest that **contains** a B-rep file.* Wedges `bin/lapidary`'s folder agent, whose
   manifest comes from `lapidary_core::is_model_file` — which still admits B-rep files on purpose.
   One `.step` file in a watched folder would have failed **every sync of that folder, for ever,
   unattended**, on a 30-second `BACKOFF`. It also uploads nothing for a hobby corpus of 400 meshes
   with one `.step` in it.
2. *Refuse only when **every** file is a B-rep file.* Never fires for a real folder drop.
   `filesFromDrop` and `filesFromInput` send every file the browser hands them and
   `Upload.tsx` sets no `accept`, so one `README.md` beside the assemblies makes the manifest
   "mixed" — and the up-front refusal is skipped in exactly the case it exists for.
3. **Shipped: refuse when the manifest holds no mesh at all.** The question is whether there is
   anything to take. If there is, take it and let the B-rep file's own job refuse it. If there is
   not, nothing needs transferring and the refusal comes before the bytes.

So four paths, one rule, and no path it can wedge. A **scan** has a job row per file, so the
`.step` file fails on its own. An **upload with a mesh in it** is taken for the same reason. An
**upload with no mesh in it** is refused up front. The **folder agent** never sends one at all,
because a 30-second retry loop is the one place a per-file refusal does not work — and it prints
the sentence once so nothing is skipped in silence. Three tests hold these open and each names in
its comment what breaks without it:
`a_drop_with_no_mesh_in_it_is_refused_before_a_byte_is_transferred`,
`a_drop_with_one_b_rep_file_among_meshes_still_takes_the_meshes`, and
`a_b_rep_file_is_not_sent_and_is_reported_rather_than_skipped`.

  `lapidary-cad/src/occt.rs` (681), `lapidary-cad/tests/occt_bridge.rs` (436), the `occt-kernel`

  `Cargo.lock` loses exactly one line (`tempfile` from `lapidary-cad`).
- **`xtask`:** `Tier::Occt` and the `occt` verify tier; `OCCT_STAGE`, `ApiTargetCarriesOcct` and
  `WorkerTargetMissingOcct` with their four unit tests. `check_targets` kept only "both targets
  exist" and lost the `FROM`-chain walk with them. `WorkflowWorkerWithoutKernels` →
  `WorkflowWorkerWithoutKernel`, which now asks for `mock-kernel` alone. `check-deploy`'s own
  fixture Containerfile no longer has an `occt` stage, so it still mirrors the real file.
- **`SERVER_FEATURES` is `mock-kernel`** in `deploy/compose.yaml` and in
  `.github/workflows/containers.yml`. The arg, the two targets and the role rules all stay: what
  separates the `api` and `worker` images is now the build arg alone, and an untargeted build
  still takes the worker's stage around a binary that refuses to start as a worker.
- **Tests flipped, not deleted wholesale.** The seven `FakeCad` cases that proved a STEP file
  *ingests* (analytic provenance, face and edge counts, `structure`/`entities`/`pmi` derivatives,
  the CAD header, the NUL-header commit, the stale CAD read) are gone with the machinery they
  describe. What replaced them: `every_b_rep_format_is_refused_by_name_and_ingests_nothing` over
  all four extensions, and the scan-walk case above.
- **`WorkerHandler.cad` → `WorkerHandler.kernel`**, `Option<Arc<dyn Kernel>>`, `None` in
  production. The field had to survive: `MeshKernel` is synchronous all the way down, so it is the
  only instant at which one of two jobs racing over one new path can be suspended, and the two
  slice-1 §3.3 race tests are staged through it. `HeldCad` became `HeldMesh` and they race over an
  STL. One other double survives — `StatesAMaterial`, keeping L3's "a typed material outlasts a
  revision whose file states another"; nothing shipped reports a header any more, but the rule is
  still reachable through `index`, and R3 takes both out with the header machinery.
- **The drop UI now shows the refusal.** `probeUpload`/`commitUpload` throw a new
  `UploadRefused` carrying the server's own sentence (the shape `createLibrary` already used), and
  `routes/index.tsx`'s upload `onError` shows it instead of `strings.upload.failed`. Without this
  the person who drops a STEP folder reads "Could not upload", which is half the error rule.

### Decided without the owner

1. **An upload is refused up front only when there is no mesh in it to take**; otherwise the
   per-file job refuses, as a scan does. The fourth option — a `refused` list on `UploadPlan`, so
   the probe could say "these I will not take" and the client skip their transfer — is the best
   answer for the person and the most expensive: a wire change, a bindings regeneration,
   `upload.ts`, and a string in a `strings.ts` block another goal owns. The cost of not having it
   is that a drop with meshes in it still transfers a B-rep file's bytes before refusing it, which
   is what a scan already does with bytes it already has. **A cheap follow-up if the owner wants it.**
2. **`bin/lapidary/src/folder.rs` was changed although no goal owns it on the board.** This goal's
   refusal broke it, so fixing it is this goal's work; `list()` now returns the B-rep paths it
   leaves out, and the watch says each once. No open goal names that file.
3. **`WorkerHandler.cad` was renamed rather than removed**, keeping an injected-kernel seam whose
   only live purpose is to suspend a job mid-parse in two race tests. Removing it means rewriting
   those two races, which belongs with R5's pass over the `Kernel` trait.
4. **A small web change was taken inside a "Rust + deploy" goal** — `UploadRefused` in
   `web/src/lib/api.ts` and one line in `web/src/routes/index.tsx`'s upload `onError` — because a
   new refusal that reaches the person as "Could not upload" fails CLAUDE.md's error rule.
   **`routes/index.tsx` is a file R1 also holds** ("the page query's card picture"): the two edits
   are in disjoint regions of it, but the lead should order that merge rather than assume.
5. **`fixtures/` went back into `.dockerignore`/`.containerignore`.** The comment there said in as
   many words that it was sent only for the `occt-test` stage.

- **Dead in `lapidary-cad`, left for R5:** `CadError::{Timeout, KernelCrashed, KernelUnavailable,

  raised them), and `classify_cad` still maps three of them to `Transient`. `CadError::UnsupportedFormat`

- **Dead in the ingest pipeline, left for R3:** `KernelOutput::{metadata, pmi, topology, structure,
  entities, provenance}` and the stage-4 header write can no longer be reached by any shipped

- **A fourth list on `UploadPlan`** (decision 1 above), if the owner wants a mixed drop to skip a

- **Stale doc lines not touched**, because another goal owns the file: `docs/ARCHITECTURE.md`,
