# A31 — A rescan reads only what changed

**Status:** open
**Branch:** `perf/rescan-unchanged`
**Wave:** 15 · **Kind:** ingest + db · **Depends on:** A30 · **Migrations:** —

## Why

Owner, 2026-10-18, "then 3 and 4". On the check stack a rescan of 3,286 unchanged files took 121 s: every mesh is read
whole and hashed again before the scan learns it already has it, and the read blocks an async worker thread. Each scan
also leaves one `job` row per file for ever (26,894 after three scans), which the queue widget counts.

## Decisions

- **A mesh whose size and modification time match its current revision is skipped without being read**, as a pack
  already is (A13). The hash stays first for anything read: a changed file, or one at a new path, is hashed before
  anything else. A file rewritten with the same size inside the same nanosecond-resolution mtime is the case this
  misses; an edit in any tool moves the mtime.
- The mesh read and hash run in `spawn_blocking`, off the async threads.
- **A scan prunes the finished file jobs of earlier, finished batches** of its library when it queues its own. Failures
  stay (they are what a person reads), and so does the scan job itself, which is how the examples know a library has
  history.

## Done when

A rescan of the unchanged check library is a stat per file; the `job` table holds one batch of done file jobs per
library; gate and rig pass.
