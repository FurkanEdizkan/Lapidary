# P3 — Tags as places

**Status:** ready at `54f411e`, gate log target/verify-P3.log — **`main` moved after the gate and the
merge is outstanding**; see "Before this merges" below.
**Branch:** `feat/tag-browse`
**Wave:** 3 · **Kind:** web (+ a small read) · **Depends on:** W0 · **Migrations:** —

## Why

Tags are how anybody actually browses a model library — "dragon", "terrain", "bracket" — and ours are a filter and
nothing more: `PUT /api/parts/{id}/tags` writes them, the facet counts them within the current grid, and there is no way
to ask "what tags does this library have" or to land on one. A tag a person cannot navigate to is a tag they will not
use.

## Facts to check before building

- The tags facet in `GET /api/libraries/{id}/facets`: it counts **within the current grid** and past
  `EXACT_FACET_ROWS` it lists values without counts. A tag index wants the whole library, which may be a different read.
- `part.tags` is a text array with a GIN index (`0022_part_tags.sql`); co-occurrence is one query over it, not a new
  table.
- The grid's `tag=` parameter and how the URL, the saved filters and the back button already handle it.
- `web/src/lib/strings.ts` — this goal's own top-level block; no other goal's is touched.

## Rules

- **No tag table.** Tags live on the part; an index is a read.
- A tag page **is** the grid pre-filtered, the same component and the same URL parameter — not a second grid.
- Related tags are earned from co-occurrence, with a floor (a tag sharing one part is not "related"), and the floor is
  stated in the UI's words.

## Stages

1. **The read** — a library's tags with counts over the whole library, and the tags most often on the same parts as a
   given tag.
   **Tests:** counts match the facet's when no filter is applied; a tag on no live part is absent; a removed part's tags
   do not count.
2. **The pages** — `/tags` (by count and by name, with a letter jump when the list is long) and `/tags/{tag}` (the grid,
   pre-filtered, with related tags beside it and an empty state that says the tag is gone).
   **Tests:** each with `fetch` mocked; the title is the tag; a tag with punctuation or a space survives the round trip
   through the URL.
3. **The chips lead somewhere** — tags on the part page and in quick look become links to their pages, and the grid's
   tag facet row links too, without losing the filter a person already has.

## Done when

Every tag in a library is reachable from `/tags`, a tag page shows the same parts the facet counted, `verify slice` is
green, and the Record says how many tags the seeded corpus produced and how deep the longest list got.

### Decided without the owner

- **Choosing a tag in the grid's facet panel goes to the tag's page**, carrying the format, query,
  category and field filters already chosen; choosing it again comes back to `/`, still with the rest.
  P3.md says a tag page *is* the grid pre-filtered, and this is that rule taken at its word: there is
  one URL for "the grid narrowed to this tag", not two. `?tag=` on `/` still works — every link
  anybody has already sent has one, and saved filters write one — it is simply no longer what the
  application writes. A saved filter carrying a tag lands on that tag's page for the same reason:
  otherwise applying one from a tag page leaves the old tag in the path and the new one in the search,
  which is two tags and one grid.
  **It costs a remount.** `/` and `/tags/{tag}` are two routes, so choosing a tag unmounts `Index` and
  mounts it again, and its local state goes with the old one: a bulk selection in progress, the staged
  part, and a scan or upload **this page started** (the `started` state behind `ScanProgress` and G6's
  review line). A batch that is in the URL survives, because `?batch=` rides along with the rest of the
  search — which is what that parameter is for. No test sees this; it is read off the router's own
  rules. If the lead would rather not pay it, the fallback is small: keep writing `?tag=` in place on
  `/`, and navigate only from one tag's page to another and from a chip. That brings back two URLs for
  one view, which is what this decision was made to avoid.
- **The related tags sit in the main column, above the grid, not in the rail.** "Beside it" was the
  goal's word and the rail is where a filter panel goes — but under `md` the rail is a drawer, and the
  two things a person on a phone most needs from this page are the suggestions and the sentence saying
  the tag is gone. Both would have been behind a button.
- **The floor is 2 and travels on the wire** (`RelatedTags.floor`), printed by the UI rather than
  restated in the copy. P3.md asks for the floor to be stated in the UI's words; a number written in
  two places is a number that drifts.
- **The index never withholds a count, where the facet does past 10k matching parts.** `DATA.md` §3.4
  offers "drop counts and show only which values are non-empty" as the way out past the threshold —
  which works for a filter panel and does not work here, because the count is the axis the list is
  ordered by. The cost is a sequential scan of the library's parts per load, marked with a
  `ponytail:` comment naming §3.4's rollup table as the upgrade. **This differs from `DATA.md` §3.4
  and the lead may want a line there.**
- **No `LIMIT` on the index and 24 on the related list.** "Every tag in a library is reachable from
  `/tags`" is the goal's own Done-when, so the index cannot be cut; the related list is a suggestion
  and a panel nobody scrolls is a better suggestion.
- **`count(DISTINCT p.id)`, which no test covers.** `PUT /api/parts/{id}/tags` drops repeats, so
  nothing reachable from the api can write the same tag on one part twice and the mutation for it
  would survive. It is kept because a row that arrived through a mirror or a bundle import went
  through no such cleaning, and `unnest` over a repeated array counts that part twice; `material_facet`
  carries it for the same reason. **The path is real:** `lapidary-ingest/src/import.rs:219` calls
  `PgParts::set_tags` with a bundle's tags verbatim, and that is the db write, not the route's
  `cleaned()`. A test could reach it through an import, and none here does.
- **The page says "models", not "parts".** These two pages are the browsing half of the application
  and the corpus they exist for is miniatures and terrain. The grid and the part page go on saying
  "part", which is what the data calls them.
- **A library that does not exist answers an empty list**, as the facets read does rather than as the
  storage read does. An empty library and a mistyped id look alike to somebody browsing, and no count
  on this page is a number anyone would believe of a library they cannot see.
- **`Index` gained `titled` rather than a `title` string.** React hoists every `<title>` it is given
  and the document takes the first in tree order; a prop that adds a second title would have left
  which one wins to whichever piece of JSX was written first. The tag route renders its own and tells
  the grid to draw none — which also keeps `routes-are-titled.test.ts` honest, since the gate reads
  the route file.

### Left for later

- **Nothing here has met a server.** Every web test mocks `fetch`; the Rust read is exercised end to
  end through the router against a live Postgres (`crates/lapidary-api/tests/parts.rs`), but the two
  halves have never spoken. The fixture api used for the screens is `target/tag-check/serve.py`.
- **No paging on `/tags`.** The whole list arrives in one response, which is what makes both orders
  free and every tag reachable. A library with thousands of distinct tags wants a cursor, and so does
  the query behind it.
- **The related read is per tag page and is not cached across them.** Walking a chain of five related
  tags is five requests, one per page, each one cheap.
- **No tag rename, no merge, no "tags nobody uses".** `dragon` and `Dragon` are two tags, as
  `PUT .../tags` keeps them; this page now makes that visible for the first time, which is probably
  where the request for a merge comes from.
- **A tag of `.` or `..` has no page.** `PUT .../tags` accepts either — it only trims and drops blanks
  — and no path segment can carry one: percent-encoded or not, a dot segment is removed before any
  router sees it. Measured: `/tags/%2E%2E` lands on the grid and `/tags/%2E` on nothing. `/tags` would
  draw a link for such a tag that quietly goes somewhere else. `?tag=..` on `/` still works, which is
  the whole of the workaround. Refusing the two at the write, or skipping them on `/tags`, is the fix
  when anybody meets one.
- **The `#` group holds anything not starting with a letter.** `28 mm`, `100% infill` and `#wip` share
  one heading. A library whose tags are mostly sizes would want that split.

### What a test cannot see, and what was looked at instead

- **Both widths, on the built page.** `target/tag-check/` holds `serve.py` (a fixture api on lane 3's
  port 33000), `shots.sh`, and `viewports.mjs`, which drives the rig's own
  `scripts/e2e/cdp.mjs`. Measured on all three screens at both widths:
  `scrollWidth == innerWidth`, **no horizontal scroll at 1440 or at 390**, and `main` fills the window
  at 1440 — no reading measure on the list, which is the `/duplicates` and `/sharing` finding applied
  before it could happen again. The lead paragraph keeps its 70ch, because that is prose.
- **A finding about the rig itself: `--window-size=390` does not lay out at 390.** Headless Chrome
  floors its window at **500 CSS pixels**; the capture is then scaled, so the PNG is 390 wide and the
  page never was. Measured directly — `window.innerWidth` and the `<main>` rect both read 500 under
  `--window-size=390,1600`, with `--headless=new` and `--force-device-scale-factor=1` alike. Only
  `Emulation.setDeviceMetricsOverride`, which `scripts/e2e/cdp.mjs`'s `session()` sets, gives a real
  390. **G5's `dashboard-390.png` was taken the first way**, so what it shows is a 500-wide layout.
  L1's are fine: `scripts/e2e/sharing-shots.mjs` goes through `session()` and so had a true 390 all
  along. The measurements above are `viewports.mjs`'s, through `session()`.
- **A crash a test could not see.** The first browser run of `/tags/dragon` — and of `/` — drew the
  crash card: `TypeError: Cannot read properties of undefined (reading 'toFixed')`. It was the fixture
  server, not the application (`/api/storage` matched a rule meant for
  `/api/libraries/{id}/storage`, so the instance panel read a `LibraryStorage`), but nothing in the
  suite would have told me the difference, and a screenshot of a crash card is what "it renders" looks
  like when it does not.
- **Five awkward tags read back out of a real URL**, in Chrome and not in jsdom's memory history:
  `/tags/28%20mm`, `/tags/jig%2Ffixture`, `/tags/100%25%20infill`, `/tags/d%26d%205e` and
  `/tags/%23wip` each draw their own tag as the heading. `%2F` was the one in doubt and it survives.
  **`.` and `..` do not** — see below; they are the one exception to "every tag is reachable", and they
  are measured rather than guessed.
- **The accessible name of a tag row is its two text runs joined.** `<span>dragon</span><span>12
  models</span>` inside a flex row computes as `dragon12 models` in the name calculation these tests
  use; Chrome inserts a space between flex children and the calculation does not, so a literal `{' '}`
  sits between them rather than a dependence on which engine is asking. **No `aria-label` on any tag
  link on either page** — the whole name is visible text, which is what WCAG 2.5.3 asks for and what a
  label of our own would risk disagreeing with.
- **The order control is marked by the router, with `activeOptions={{ exact: true, includeSearch:
  true }}`.** Both links point at `/tags`, and the router's default partial search match makes "Most
  used" — whose search is empty — a subset of `?order=name`, so without `exact` both read as the
  current one. Caught by a mutation, and now by a test on the A-to-Z page.

### Numbers

- **Tags the seeded corpus produced: zero.** Nothing writes `part.tags` but `PUT /api/parts/{id}/tags`
  — no migration seeds one, no fixture carries one, ingest never reads one off a file
  (`crates/lapidary-api/src/tags.rs` says so in its first paragraph), and the e2e rig writes none.
  **The bundle importer is the one other writer** — `lapidary-ingest/src/import.rs:219` carries a
  bundle's tags through verbatim — but nothing seeds a bundle either. So on a stack built from `main`
  today, `/tags` is the "nobody has tagged
  anything yet" sentence, for every library. **This is the lead's decision**, not mine: the owner's
  corpus is 54 creators of miniatures and terrain, and the discovery half of this application has no
  data until either P1's release import brings tags in with a pack or somebody types them. The read,
  the pages and the chips are all correct and all empty.
- **The longest list looked at: 50 tags over 26 letter groups**, the fixture corpus in
  `target/tag-check/serve.py` — a plausible creator library (`28 mm` 412, `pre-supported` 268,
  `terrain` 194, down to `resin` 2), including a tag with a space, one with a slash, one with a
  percent, one with an ampersand and one starting with `#`. Six columns at 1440, one at 390. The
  letter jump appears past 40 tags and drew 26 links, every one of them pointing at a heading that
  exists.
