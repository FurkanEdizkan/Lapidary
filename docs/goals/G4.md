# G4 — Dashboard resolve

**Status:** ready at 0ac8417, gate log target/verify-G4.log
**Branch:** `feat/dashboard-resolve`
**Wave:** 2 · **Kind:** Rust · **Depends on:** W0, G3 · **Migrations:** —

## Why

A dashboard of twelve widgets must settle in one round trip, and one slow widget must not hold the other eleven.
Design: [`phase-6.md`](phase-6.md) § Dashboard.

## Facts checked (re-check against W0's and G3's merges)

- W0's `Widget` enum (seven kinds), `ResolveRequest`, `ResolveResponse`, `KeyResult`, `dashboard::routes()` (empty).
- G3's `likeness::clusters(db, library, since)` for the duplicates widget.
- The pool is `max_connections(8)` (`crates/lapidary-db/src/lib.rs:456`). Existing reads to reuse: library storage,
  instance storage (skip its disk walk), facets, the grid page (`parts.rs` `page`), saved filters.

## Rules

- Owns: the handler and resolvers in `crates/lapidary-api/src/dashboard.rs`; pulling the grid helper shared by `page`
  and the `savedFilter` widget out of `parts.rs` `page`; `crates/lapidary-db/src/dashboard.rs` (new, queue counts);
  `crates/lapidary-api/tests/dashboard.rs`.
- A `JoinSet` with a semaphore of 4; each key's 2 s timeout starts once it holds a permit.

## Stages

1. `POST /api/dashboard/resolve` — 1–32 unique keys (else 422); always 200, results in request order, each `ok`,
   `timedOut` or `failed`; an unknown library or filter fails only its key.
2. **Tests:** 12 widgets of all seven kinds → 12 `ok` in order; 33 widgets → 422; duplicate keys → 422; one key
   blocked by `LOCK TABLE job IN ACCESS EXCLUSIVE MODE` held on another connection → that key `timedOut` after about
   2 s while the other eleven are `ok`; three concurrent 12-key resolves all succeed.
3. **Measured:** p50 of a 12-widget resolve on a 10,000-part library.
4. Mutation checks: the semaphore removed (keys time out on the pool), the timeout started before the permit.

**Decided without the owner.**

1. **A limit past its cap is clamped, not refused.** `phase-6.md` gives `recent` and `savedFilter`
   twelve and W0's `limit: u8` cannot carry it, so the handler clamps to `1..=12` (and a facet to
   `1..=24`, where the design sets no figure). 422ing a whole dashboard because one tile asked for
   twenty cards would take down eleven tiles that were fine, and a widget is a read. Zero is one, for
   `parts.rs`'s reason.
2. **Only four of the seven kinds probe the library.** `recent`, `facet`, `queue` and `duplicates`
   answer emptily for an id naming nothing, so each asks `PgParts::auto_thumbnail` first — the probe
   `derive.rs` and G3's routes already use. `storage` and `savedFilter` say so through their own read,
   and `instanceStorage` names no library. Probing anyway would be a second round trip that changes no
   answer.
3. **The semaphore is per request.** A process-wide one needs a field on `AppState`, and every test
   file in the workspace builds that struct literally — other goals' files, this wave. What per request
   costs, stated plainly: three resolves can put twelve keys in flight against eight connections, and
   `three_resolves_at_once_all_answer_every_key` passes because these reads are fast rather than
   because the pool is held back. It is the same ceiling as the first item under "left for later".
4. **`instanceStorage` skips the disk walk *and* the flush of pending reads.** The walk is a `stat`
   per file and behind `?onDisk=true` on the route for that reason; the flush is a write, and a
   dashboard is a read. The figure it affects — the render cache — is then at most five minutes behind,
   which is what `GET /api/storage`'s own warning already tolerates. The exact figure is on the storage
   page.
5. **A saved filter whose category was deleted fails its key** rather than showing an empty tile.
   `filters.rs` promises the grid says the category is gone instead of showing nothing, `FilteredParts`
   has no room to say it, and an empty tile reads as "nothing matches".
6. **The facet tile's "commonest" is sorted in Rust.** The facet reads answer in value order; past
   `EXACT_FACET_ROWS` (10,000 matching parts) there is no count to sort by at all, and the stable sort
   then leaves value order, which is the only order left. A library that big gets an alphabetical tile
   and no counts, exactly as its sidebar does.
7. **`duplicates` reuses G3's `clusters` and throws the cards away.** One definition of a cluster is
   worth the waste; the `ponytail:` comment names it and the count-only read that would fix it.
8. **`grid_rows` refuses in two shapes.** `fields::filter_of` composes a whole `Response` whose text
   cannot be read back out, so the helper returns `GridRefusal::Field(Response) | Db(DbError)`: `page`
   returns the one and wraps the other, and a widget turns each into a message of its own.
9. **The queue counts are one pass over the library's `job` rows**, `done` ones included.
   `job_active_idx` is partial on pending/running and nothing indexes `failed`; migration `0036`
   measured the same shape at about 1.4 ms over 10,001 rows, and this goal was given no migration
   number.

**Left for later.**

- **The 2 s timeout does not stop the statement.** Cancelling the future leaves the query running on
  the server, and sqlx cannot return that connection to the pool until it answers — which
  `a_key_that_gave_up_still_holds_its_connection_until_the_lock_clears` states on a pool of one. So the
  permit limit bounds how many keys wait at once, not how many connections keys that gave up still
  hold, and a long-held lock plus repeated resolves can drain the pool of eight. The fix is a
  server-side `lock_timeout`/`statement_timeout` on the pool `lapidary_db::connect` builds, which is
  not this goal's file. **This is the one thing here worth another goal.**
- A partial index on `state = 'failed'` for the queue tile, when a library accumulates enough failures
  to measure. Needs a migration.
- A count-only near-duplicates read, so the `duplicates` tile stops building cards it discards.
- The measurement times the twelve tiles together and not one at a time: what the 122 ms is spent on is
  not broken down. The locked-table tests are what say the slow tile cannot hold the others.
