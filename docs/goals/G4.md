# G4 — Dashboard resolve

**Status:** open
**Branch:** `feat/dashboard-resolve`
**Wave:** 2 · **Kind:** Rust · **Depends on:** W0, G3 · **Migrations:** —

## Why

A dashboard of twelve widgets must settle in one round trip, and one slow widget must not hold the other eleven.
Design: [`phase-6.md`](phase-6.md) § Dashboard.

## Facts checked (re-check against W0's and G3's merges)

- W0's `Widget` enum (seven kinds), `ResolveRequest`, `ResolveResponse`, `KeyResult`, `dashboard::routes()` (empty).
- G3's `likeness::clusters(db, library, since)` for the duplicates widget.
- The pool is `max_connections(8)` (`crates/lapidary-db/src/lib.rs:456`). Existing reads to reuse: library storage,
  instance storage (skip its disk walk), facets, the grid page (`parts.rs` `page`), saved filters.

## Rules

- Owns: the handler and resolvers in `crates/lapidary-api/src/dashboard.rs`; pulling the grid helper shared by `page`
  and the `savedFilter` widget out of `parts.rs` `page`; `crates/lapidary-db/src/dashboard.rs` (new, queue counts);
  `crates/lapidary-api/tests/dashboard.rs`.
- A `JoinSet` with a semaphore of 4; each key's 2 s timeout starts once it holds a permit.

## Stages

1. `POST /api/dashboard/resolve` — 1–32 unique keys (else 422); always 200, results in request order, each `ok`,
   `timedOut` or `failed`; an unknown library or filter fails only its key.
2. **Tests:** 12 widgets of all seven kinds → 12 `ok` in order; 33 widgets → 422; duplicate keys → 422; one key
   blocked by `LOCK TABLE job IN ACCESS EXCLUSIVE MODE` held on another connection → that key `timedOut` after about
   2 s while the other eleven are `ok`; three concurrent 12-key resolves all succeed.
3. **Measured:** p50 of a 12-widget resolve on a 10,000-part library.
4. Mutation checks: the semaphore removed (keys time out on the pool), the timeout started before the permit.

## Done when

Tests and the p50 in the Record, `verify slice` green, handed off.
