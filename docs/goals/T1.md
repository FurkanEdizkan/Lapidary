## Why

Three harnesses have driven this application — `target/docker-check/check-plain.sh` (goal 8),
`target/docker-check/group/run-group.sh` (goal 9), `target/ui-verify/verify.mjs` (the UI refinement) — and all three
were scratch: each goal wrote one and threw it away. The board already asks for a fourth (W3: "both Phase 6 exits
measured on the merged `main` through a compose stack on a lane port block") and the backlog asks for a fifth (the
1,000-part UI sweep). This is that tool, committed once, so W3, G5, G6, L1 and every later goal run it instead of
writing it again.

It is also the first end-to-end test this repository has had. The 31 web test files (~330 tests) all run in jsdom with
`fetch` stubbed; nothing has ever asserted that the real api, the real worker and the real browser agree.

## Rules

- **Owns** `scripts/e2e/**` (new) and this file. Nothing else. `scripts/` was B0's; the lead grants this subtree.
- **The owner allowed Docker image builds for this goal** (`PROTOCOL.md` forbids them otherwise). Never
  `docker builder prune`, `docker volume prune`, `docker system prune`, and never remove an image not named
  `lapidary-e2e-*`.
- **One compose function with `-p` hard-coded**, used by every call. No bare `docker compose -f deploy/compose.yaml`
  anywhere in the rig: that is the owner's project.
- The override file carries **`ports: !override` and `extra_hosts` only** — never `build:`, `target:`,
  `SERVER_FEATURES` or `LAPIDARY_ROLE`, because `check-deploy` cannot see this file and a role or kernel mistake in it
  would be invisible to the gate.
- **Ask the lead before `build` or `up`.** Only ~4 GiB of RAM is available and two Rust lanes are compiling in this
  wave; the lead says when the machine is free. Everything heavy goes through `cargo xtask heavy -- …`.
- Every output goes under `target/e2e/` — a full `/` loses all tool output.

### Stage 0, second pass — five things that would have made stages 2-6 lie

Reviewed before spending any of the machine time the lead has to free up, because each of these would
have cost a run:

- **`drive` always exited 0.** The flows' exit code was echoed inside the `{ … } | tee` block and then

  with, and the next `up` would fail authentication blaming the wrong thing. `PIPESTATUS[0]` is now
  checked and `down` refuses to delete anything after a failed teardown.

  and the grid's count line is computed in the browser. Two flows compared one: `remove-restore` was
  asserting `undefined === undefined`, **a pass that tested nothing**, which is exactly the silent pass

  empty states that nothing was covering.
- **The grid's preferences leaked between flows.** Page size, order, density and layout live in

2. **20 of the 1,000 corpus symlinks dangle** — one directory's targets have gone from `/mnt/Storage2`
   since the corpus was made — and **all 20 are inside the smallest 400**. Taking rows 1-400 blind either
   aborts or leaves a 380-file library and breaks the paging arithmetic "400 is the number" rests on. The
   slice is now the smallest 400 *that exist*: **400 files from 420 rows, 915 MiB** (the 861 MiB figure is
   the first 400 rows; reading 20 further down costs 54 MiB more).
3. **`rm -rf` on a bind-mount source replaces the inode, and the mount follows the inode.** Rebuilding
   the ingest tree left the worker looking at the old deleted directory: `/ingest` was empty, the walk
   reported `total=1 ingested=0`, and it read exactly like a broken scan route with no error anywhere.
   Host inode 16909401 against container 16908512 is what it looked like from outside. The contents are
   cleared now rather than the directory, and a new check compares the host's file count with what the
   worker sees — on both the fresh and the reused path, since a tree kept across a `down` is the case
   where a stale mount survives.
4. **The upload sent its chunks without reading the plan.** `POST /uploads/probe` answers
   `UploadPlan { have, needRows, needBytes }`, and those three are the whole protocol — `needRows` means
   the store already has the bytes and **nothing should transfer**. `check-plain.sh` sent regardless
   because it only ever ran against an empty library; against one that already holds the file every PUT
   is refused, correctly, with nothing staged to write into. "Hash first, always" is what makes the plan
   possible, and ignoring it is what made this rig look broken on its second run.

And the two that reported success while testing nothing:

- **The failure list asked for `message`.** `JobFailure` is `{job, path, reason, attempts}`, so every
  reason came back as `''` and **five real errors were hidden behind an empty string**. There is now a
  check that no failure has an empty reason, since one would break this repository's own rule that errors
  say what broke and what to do.
- **`ingested` is a per-batch counter, not a library fact.** A correct re-seed against a library that
  already holds the tree ingests nothing, so the check read `ingested=4` and failed on a library that was
  perfectly right. It asserts the **part count** now.
- **An edit to one function deleted the four helpers defined beside it**, and `bash -n` is blind to that: a
  missing function is a runtime name lookup, not a syntax error. So `stack.sh` parsed perfectly, printed
  `command not found` at every call, **ran the seed to the end and wrote a `seed.json` with 0 checks in
  it** — a file that looks exactly like a pass. `check.sh` now asserts all 33 of `stack.sh`'s functions
  exist, and the mutation harness proves that check is not vacuous. The helpers also moved away from the
  function whose rewrite took them.
- **`drive` had the same hole one level up.** Its report defaulted `flows.json` to `[]` and exited 0, so
  anything that killed `flows.mjs` outside a flow — Chrome not opening a debugging port, a `session()`
  throwing, `--only` matching nothing — reported green with no rows. It now fails on an empty row list and
  on a non-zero `flows exit`, `flows.mjs` saves its rows from an exit handler, and the hole is closed
  against a live test: `drive --only nosuchflow` exits 1 and says *"the flows wrote no rows at all"*.

And two findings that are about the world rather than the rig:

### Findings

**Inside T1, fixed here:**

- The corpus root is `corpus-1000/STL Files/`, one level below what Facts checked said. Both facts corrected above.
- The smallest 400 corpus rows are **861 MiB, not ~200 MB** — a factor of four. 400 stays; the scan estimate moves.
- `verify.mjs`'s transport is unsafe to copy and `cdp.mjs` takes `open-timing.mjs`'s instead: `verify.mjs`'s `evaluate`
  returns `undefined` on an exception, so **an assertion written against it passes silently on a page that threw**; its
  port is a fixed 9400 (two lanes collide); it leaks a profile per session.
- A JS `matchMedia('(hover: hover)')` shim is **not sufficient**. Tailwind wraps every `hover:` utility in
  `@media (hover: hover)`, which script cannot reach, so the category tree's per-row Share/Rename/Delete stay
  `opacity-0 pointer-events-none` and a coordinate click lands on the row underneath. `cdp.mjs` emulates the CSS
  features (`hover`, `any-hover`, `pointer`) *and* keeps the shim, because `Card.tsx`'s turntable asks the JS query
  directly. Anybody reusing `verify.mjs` inherits the gap.
- **Paging has no next/previous control**, contrary to stage 4's flow list: it is an `IntersectionObserver` sentinel
  plus one `Load more` button. An `IntersectionObserver` never fires in a tab that is not frontmost, so `cdp.mjs` calls
  `Page.bringToFront()` — without it the grid simply will not page and it reads as an application bug.
- **The quick look is not a dialog at ≥1280 px** — it is a non-modal `<aside>` with no focus trap, and the same
  children are a modal dialog below 1280. The flow asserts which shape it got, at both widths.
- `DOM.setFileInputFiles` **cannot drive a folder upload**: `lib/upload.ts` reads `webkitRelativePath`, which is empty
  for injected files, so a driven upload is always a flat drop and creates no category. The `upload` flow asserts parts
  and never folders. A folder upload is hand-testable only.
- Reading `.lane.env`: a variable that is **present and empty** must reach the refusals rather than be refilled from
  the file (`${var+set}`, not `${var:-}`). The refusal test found this — before the fix, clearing a port silently
  restored it.
- A backtick inside a `//` comment that sits **inside a template literal** ends the literal. `node --check` caught it;
  nothing else would have. Worth knowing for any harness written this way.

**The compile lock, measured — for the lead, because W3 pays it:**

Everything heavy goes through `cargo xtask heavy`, as the lead asked, and the lock did its job: no run of
this rig ever coincided with another lane's compile. The cost is that it queues. Over this session the
rig's `up` and `seed` waited behind **four separate `cargo test --workspace --all-features` runs** from
other lanes, each wait longer than the work that followed it — an `up` that takes **7 s** waited about
**two minutes**, and the 25 s seed waited longer still. Two observations, both the lead's call:

- **`up` compiles nothing.** It is `docker compose up -d --no-build`. What it actually needs is memory, not
  the compile lock, and it already guards on available RAM ≥ 5 GiB. Taking the lock for it buys
  coordination against a build starting *afterwards*, which the lock cannot give anyway since `up` holds
  it for only 7 s. Left under `heavy` here because the lead's instruction said so; worth revisiting.
- **The seed genuinely competes**, but less than expected: the worker peaked at **52 MiB against its 2 GiB
  ceiling** and the whole scan is 25 s. The 4.3 GB of declared ceilings is a ceiling, not a reservation.

**For the lead to file:**

- `scripts/claim-goal.sh`'s `LAPIDARY_PORT_*` block now has its first consumer. **Lane 0 — the lead's own main
  checkout — has no port block**, so `stack.sh` refuses there until `LAPIDARY_PORT_WEB=30000`, `API=30080`,

- **A decision needed:** stage 2 wants `target/e2e/<lane>` "empty and removable" after `down`, but stage 6's
