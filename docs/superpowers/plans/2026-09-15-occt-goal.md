# Goal 4: OCCT, and what it unblocks

Written 2026-09-15. **This file is the goal's source of truth.** After any context summary, re-read it
together with ROADMAP's "Open points, 2026-09-15" section and this goal's record there, which is the
progress ledger.

Run it first of goals 4–6: goal 5's STEP materials and centre of mass need the bridge this goal rebuilds.

## Why

Most of what is still open after goal 3 waits on a real CAD kernel: STEP diffs, snapping to curved
surfaces, PMI drawn in the view, explode view, format negotiation, and Phase 4's FreeCAD round trip. The
owner chose to build the OCCT image now (2026-09-15), knowing Docker is shared with another project.

  `docker build --target occt-test`. The Phase 0 exit test (`crates/lapidary-cad/tests/occt_bridge.rs:192`)
  timed the 200-part fixture at 111 ms.
- **How the worker reaches OCCT.**
  - One `occt-bridge convert` subprocess per job, writing `mesh.stl`, `parts.json`, `structure.json`,
    `entities.json`, `pmi.json`, `measurements.json` and `header.json` (`crates/lapidary-cad/src/occt.rs:100-135`).
  - `OcctKernel::new` runs `occt-bridge version` at start (`occt.rs:49-71`), and the server finds the
    bridge by name on `PATH` (`bin/lapidary-server/src/main.rs:453`).
  - The bridge has no RPATH, so it needs `LD_LIBRARY_PATH` (`sidecar/occt-bridge/README.md:118-121`).
  - The image is Debian trixie (glibc 2.41); this host is Ubuntu 24.04 (glibc 2.39). The host has no
    `cmake`, no OCCT and no FreeCAD.
- **Compose** can run without `web`: `docker compose -f deploy/compose.yaml up db api worker`. The worker
  is built with `SERVER_FEATURES: mock-kernel,occt-kernel` (`deploy/compose.yaml:128-135`).
  `deploy/.env` holds the local `POSTGRES_PASSWORD` and is never overwritten.
- **Disk.** Root had 24 GB free on 2026-09-15, and Docker lives there. Each `verify occt` run leaves an
  untagged ~2.9 GB `occt-test` image, sharing most layers (memory note: root disk fills from Docker).
- **Fixtures.** `fixtures/step/` holds the only STEP and IGES files: the 200-part, three-level

## Stages

Each stage with code gets its own branch, merged before the next starts. Defaults are stated; list each
one you take under "Decided without the owner" in this goal's ROADMAP record.

### 0. Preflight (no branch)

- `lapidary-test-db` is up, and `cargo deny check` passes on `main`.
- `df -h /` shows at least 15 GB free. Stop and ask if it does not; never prune to make room.

### 1. The image, and a real kernel beside the native stack (no branch unless code changes)

- Run `cargo xtask verify occt` in the foreground, logged to `target/`. Record its wall time and the
  disk it took.
- Build the `occt` stage under a local tag, `docker create` it, and copy `/opt/occt/lib` and
  `/usr/local/bin/occt-bridge` into `target/occt/`. Remove the container.
- Check the copies against this host: `objdump -T` for `GLIBC_2.4x` symbols, then `occt-bridge version`
  and `occt-bridge selftest` with `LD_LIBRARY_PATH=target/occt/lib`.
- **If they run,** a native `lapidary-server --features occt-kernel` worker takes `target/occt/bin` on its
  `PATH`, beside the native api and `vite preview`, as goal 2's measurements ran.
- **If they do not,** build the `worker` target and run `docker compose -f deploy/compose.yaml up db api
  worker`, with the web app native against it.
- **Afterwards** remove this goal's own dangling `occt-test` images, and nothing else.
- Record in ROADMAP how to start the OCCT worker, so goal 5 does not work it out again.

### 2. Checks on the fixtures (no branch unless a finding needs code)

- **Phase 0 and Phase 2, timed again** on the fixtures: `verify occt`'s printed Phase 0 figure, and a scan
  of `fixtures/step/` through the stack as Phase 2 was timed. Record them as fixtures, not real-world files.
- **A section cut through the 200-part assembly** with parts hidden, in headless Chrome with a throwaway
  profile: no cap across a hidden part. Screenshot it.
- **The assembly as a bundle.** Export a controlled library holding the 200-part assembly and the three
  cylinders, each with a second revision; import it into another library. Lineage identical, row by row,
  as slice 2's 40-part check compared it. Record the reading: one assembly of more than 40 placed parts
  satisfies Phase 5's "40-part assembly".

### 3. CAD derivatives on demand: `feat/cad-derivatives-on-demand`

- The derive arm for `structure`, `entities` and `pmi` fetches the source and runs the kernel with that
  product, as ingest does, instead of refusing.
- A startup sweep queues it for CAD-format revisions with no `pmi` row. Default: only the current
  revision of each part that is not removed.
- **Tests:** with the mock kernel, a STEP revision missing its rows gets them from one job; a second sweep
  queues nothing. Mutation-check both.
- **Check:** delete one fixture part's `pmi` row on the stack, restart the worker, and the part page lists
  its PMI again.

### 4. Face and edge counts: `feat/face-edge-counts`

- The bridge writes `face_count` and `edge_count` into `measurements.json` (every face and edge of the
  shape, analytic or not). Rebuild the `occt` stage.
- A migration adds the two nullable columns to `revision`. Mesh revisions stay null, and the diff leaves
  them out.
- Carry them through `RevisionDiff`, the api's figures and the Compare table, exact when present.
- **Tests:** `occt_bridge.rs` asserts the plain cylinder's counts (3 faces; confirm the edge count against
  the shape rather than assuming); the diff test covers present and absent counts.

### 5. Snapping to cones, spheres and tori: `feat/snap-curved-surfaces`

- **Defaults:** a sphere reads its diameter; a cone reads its half-angle and, where a pick lies on it, the
  diameter at that height; a torus reads its tube diameter. All exact, from the entity.
- **Tests:** unit tests in `web/src/lib/measure.test.ts` for each, on entities shaped like the bridge's.
  Mutation-check one per surface.
- **Check:** a fixture with a cone and a sphere. Default: add one to `generate-fixtures`
  (`main.cpp:809`), as its own commit, if no fixture has them.

### 6. PMI in the view, on analytic faces: `feat/pmi-in-view`

- Each annotation on a plane, cylinder, cone, sphere or torus face is drawn at that face's entity origin
  and axis or normal, through the placements in `structure.json`, as a label beside the face.
- A toggle beside the PMI list, off by default. The list stays the source of truth.
- Annotations on freeform faces stay in the list, and the list says why they are not drawn. Recorded:
  per-face triangle ranges in the GLB would place those.
- **Tests:** the anchor maths as a pure function, per surface kind, with a placement applied.
- **Check:** `cylinder-d22-pmi-lp-9012-00.step` in the browser, labels on the cylinder and the datum face.

### 7. Explode view: `feat/explode-view`

- Split the current rung into one mesh per placed part by `extras.parts`, and move each along the vector
  from the assembly's centre to the part's centre, scaled by a slider from 0 to 1.
- Hidden parts stay hidden. **Measuring is off while exploded**, and the bar says so: a distance across
  moved parts would be a figure about a shape that does not exist.
- Only rungs with `extras.parts` offer it; a single mesh does not.
- **Tests:** the offsets as a pure function; the measure bar disabled while the slider is above 0.
- **Check:** the 200-part assembly exploded and put back, screenshots at 0, 0.5 and 1.

### 8. Phase 4's exit on Linux (no branch unless code changes)

- **Ask the owner** whether FreeCAD is installed when this stage starts. If not, skip to stage 9 and come
  back once it is.
- `lapidary register`, then a `lapidary://open` link from a controlled library's STEP part opens the
  checkout in FreeCAD.
- Change the part, then File → Export as STEP over the checked-out file's own path. The watcher takes back
  only that name and format.
- A new revision appears with origin `agent`, and its diff shows exact volume and the face and edge counts
  from stage 4. Record the times as slice 1 recorded them.
- Record that macOS and Windows are still open.

### 9. If time remains: the `Target` trait: `feat/target-trait`

- A bridge `export` command: STEP or IGES to STL and 3MF. Rebuild the `occt` stage.
- A derivative kind for each export, produced on demand and served as a download variant named
  `*.lapidary.stl` / `*.lapidary.3mf`. `variant=original` stays byte-identical.
- The trait with its two first callers: the download route, and `lapidary open` choosing the format a
  registered tool takes. Default: an STL for a tool whose desktop file declares `model/stl` and not STEP.
- **Tests:** negotiation picks original when the tool takes the source format, and an export otherwise;
  a download variant is never the original under another name.

## Recorded, not built

- Datums no tolerance refers to: OCCT's STEP reader only creates a datum a tolerance refers to, so this
  needs reading `DATUM` entities from the model or patching OCCT, and a fixture OCCT's writer cannot make.
- AP242 files written by other CAD tools: there are no licence-clean files here.
- Timing Phase 0 and Phase 2 on real-world STEP files: none on this machine.
- The macOS and Windows parts of Phase 4's exit.
